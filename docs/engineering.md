# Engineering guide

This document owns implementation boundaries, technical constraints and testing policy. Game semantics belong to the [specification](story-format-spec.md), editorial choices to the [authoring guide](story-authoring.md), and commands to the [README](../README.md#tools).

## Boundaries

- Use one parser/model and one deterministic game core for the browser, linter, checkpoint planner and logical runner. Do not copy transition logic into individual clients.
- Story semantics stay in `src/engine/`; browser code owns geometry, pointer handling, dialogs and local storage. The engine retains finite move coordinates exactly; the browser constrains drops and new creations using measured tile bounds, rather than fixed text-card limits.
- Parsing preserves file/line provenance, section headings, declarations, qualifiers and explicit/default fate distinctions. Every diagnostic and related location has a UTF-16 text span into the original buffer, including CRLF offsets, as well as readable source locations. Related locations include explanatory messages, not just addresses.
- `Story.sourceReferences` retains authored declaration/use spans before recipe deduplication. Declaration lint and language-service navigation share this provenance, including forward references, explicit identities and inherited shorthand. Resolve declaration requirements over the whole manuscript in fast lint; keep provisional parsed identities available to incomplete previews. Unresolved references prevent deep analysis, never raw-draft saving. Do not infer chapter supplies from declaration validation or add generated installation uses to the unused-declaration count.
- Node-only story discovery and file I/O live outside browser modules. The browser fetches ordinary Markdown and artwork files; Vite bundles application code and generates catalogue metadata. See the [loading routes](../README.md#run-the-game).
- Ordinary saves are versioned action histories bound to a story fingerprint. Replay reconstructs logical state; browser positions are presentation metadata. Edited previews need the separate snapshot boundary described below because changed rules cannot replay the old history faithfully.
- Item stacking is browser presentation metadata alongside positions: persist it in saves, interaction anchors and chapter-entry snapshots, and remap identities during live edits. Append new identities and raise picked-up items; feedback CSS must not override their order. See the [dragging contract](ux.md#work-surface-and-dragging).
- New-result placement uses the engine's computed receiver status after retention checks. Capture the receiving tile's rectangle before rendering removes it; then use measured result dimensions to centre a replacement or find adjacent space. Compound fitting updates the existing owner without applying new-result placement.
- Hotspot drop resolution lives in `engine/hotspot-drop.ts` and uses legal actions, actual occupants and the receiving chapter. Pointer preview and release use the same resolver. `place:` references do not enter the item registry. Shared hotspot markup, sizing and rectangle calculations serve gameplay and geometry lint; the CLI measures with Chromium only for manuscripts containing placements, and the live editor measures all declared hotspot surfaces at the reference width after artwork preparation. Geometry measurements travel with the diagnostic revision into the worker.
- A successful authored result snap is recorded as `resultPlacement` on its combination action. The browser first resolves dispositions and measures the result, then replays that one action with the chosen placement so hotspot membership, goal latching and restoration remain engine-owned. Occupancy fallback leaves the normal action unchanged. The engine validates the destination's hotspot context, applicable authored entry and finite coordinates; browser geometry remains responsible for rectangle containment and collisions.
- Logical observations expose only normal player information. Keep developer recipes and checkpoint routes out of fresh-player observations; the [README protocol](../README.md#logical-playtesting) defines the runner's interface.
- Apply the [archive policy](../archive/README.md) when consulting historical implementations.

## State and continuation analysis

Token statuses record visibility and incorporation, while `State.excluded` records permanent exclusive choices. Hidden tokens remain in state. The browser encyclopedia derives distinct described identities from all current tokens, never only available tokens. Each token records immutable first-encounter chapter/order separately from its mutable placement chapter. Supplies and creations stamp the current progression chapter; moving, carrying, retiring and installing do not change it. Ordinary old saves reconstruct this metadata through replay. Edited snapshots retain/remap valid metadata; legacy edited history that cannot be safely reconstructed is explicitly grouped as earlier discoveries, not guessed from current placement. Chapter/story restoration restores inventory and encounter metadata together. Keep chapter progression, goal latching, slot installation and input hiding in the shared engine so browser and logical play agree.

Assess candidate hidden inputs jointly at the combination event. Do not independently approve two removals that together block progress, or retroactively hide retained inputs on unrelated actions or reload. Include every unfinished goal in each `next:` chain in continuation checks, even if the chain's final goal has already been achieved. Use the same complete-chain predicate for chapter completion and skipping; sequential display never waives a predecessor. These are implementation obligations for the specification's protection rules.

The analysis enumerates unresolved exclusive pairs, then computes reachable constructions with the chosen branch and chronological hotspot availability. It has an explicit limit of 12 unresolved exclusive pairs rather than silently claiming exhaustive analysis after truncation. This is an implementation of the specified retention model, not an independent formal proof of its invariant.

The separate content-opportunity linter plans sets of goal/target dependencies backwards, deduplicating constructed identities and installed slots before combining independent goals. It evaluates each set with one working state through the shared engine; it does not enumerate partial action subsets. Chapter histories store independent OPTIONAL records and collapse pessimistically without expansion. Retirement is assessed against the completed construction set, rather than inherited from a representative playthrough. Histories with the same available inventory can merge retired-versus-uncreated intermediates. Keep their possible noncreation separately from creation blockers: losing future alternatives must not accidentally give another ingredient extra cleanup protection. The engine's optional retirement-check callback supports this abstract query while ordinary gameplay retains its default continuation policy. Explanations describe observed blockers and source rules; they must not change analysis outcomes. The [lint specification](story-format-spec.md#opportunities-for-authored-content) owns the calculation and its deliberate losses. Stop above 100 distinct alternatives and report an analysis-limit error without unreachable-item findings. Keep small, explicit gameplay counterexamples as regression fixtures. Statistics must distinguish construction-set evaluations, engine operations and maximum family width.

## Tests that earn their cost

The full default suite should finish in about 20 seconds. It includes semantic tests and Chromium interaction checks. Keep cases small and purposeful: parsing ambiguity, jointly hiding inputs, exclusive branches, compound preservation/wrapping, goal latching, hidden-information boundaries, real drag/reload/reset, and one complete legal witness for each active story.

Do not snapshot whole stories, pin incidental counts or rerun historical tests. A change in wording is not a reason to rebuild a large expected-output fixture. Add a regression case when a real counterexample exposes an important semantic boundary. Compare semantic state rather than string snapshots of large UI markup. Run timing checks when new tests or code make them relevant. Archive hash verification is an occasional preservation check, not part of each development test run.

## Browser implementation

The story cover is a presentation gate, not an engine action. Unstarted covers do not persist game progress; Start captures the ordinary arrival state, while valid existing saves and explicit debug checkpoints bypass the gate. Pre-start live edits regenerate a fresh initial game rather than reconciling inventory the player has never seen. Story restart removes only that story’s progress before returning to its cover; chapter restart restores its existing arrival snapshot and popup.

Cover and chapter rendering share viewport geometry. Keep stored positions and authored hotspots in the 390 × 844 reference scene; scale and crop it uniformly, with measured visible bounds for drops and result placement. Clip the world's transformed overflow so it cannot extend the scroll range. Chapter offsets use the available viewport height, not the reference image height. Save the viewport height with scroll anchors and normalize them on restoration. During resize, retain the last deliberate scroll position before browser layout clamps it; incidental resize scroll events must not become authoring interaction anchors.

Scenery and the interactive board use separate stacking contexts with the same scene geometry and scroll container. Place the fixed goals and debug control together between those layers; use native paint order and hit testing instead of clipping holes around items. Transparent board space passes input through to uncovered controls, while items and hotspots retain their own hit areas. Preserve background image nodes when moving from the cover to the first chapter and during reconciliation.

Arrival layout is a browser-only geometry operation shared by icons and text cards. Capture each retained token's placement chapter before advancing the engine, independently of its immutable encounter metadata. Pass measured visible bounds, goals, item sizes and hotspot shapes to the layout; capture the completed arrangement in the chapter-entry snapshot. Circular hotspot pointer targets, clearance and placement lint share the inscribed-circle geometry with the minimum touch diameter. The [UX arrival contract](ux.md#chapter-arrival-layout) owns ordering, reservations and exceptions.

Tutorial markers retain authored source/chapter provenance separately from deduplicated recipes. Count/chapter checks run in fast lint; first-move readiness uses shared engine recipe matching in deep lint. The browser uses that same directed action, with a separate decorative overlay and per-manuscript completion store. Cloned visuals carry no game identities or focus targets. The engine discovers two-item hotspot tutorial opportunities from current ingredients, fittings, result eligibility and normal hotspot drop resolution, including a hypothetical preparatory placement. The browser verifies the demonstrated next drop against measured targets. Keep opportunity selection stable while valid, and select visible cues by the priority in UX. Only actual accepted combinations and deliberate goals activations record accomplishments; checkpoint generation is not tutorial evidence. The [UX tutorial contract](ux.md#contextual-tutorials) owns sequencing, persistence and reset behavior.

Implement the interaction contract in [UX](ux.md). Preserve connected image and scene DOM nodes rather than replacing the world after each move; do not rewrite unchanged image URLs. Suppress native HTML drag, own pointer timers and capture through completion, cancellation, focus loss and resize, and measure long labels as well as simple physical-item names. Test real pointer events, and distinguish browser touch emulation from a native-device test.

The stable game container owns pointer capture; item reconciliation must not cancel an otherwise active drag. Capture loss with no buttons held can precede `pointerup`; retain the gesture for the document release handler instead of treating that ordering as cancellation. Capture loss while still pressed, `pointercancel`, focus loss and resize retain their cancellation paths. Preview and release share measured destination geometry, retaining the pickup offset and resolving the final rectangle directly from release coordinates before restoring visuals. The browser drop resolver projects engine legal actions and useful placement hints onto the eligible geometry; cache those choices only for the current gesture and keep target geometry live through scrolling. Hover replacement cancels obsolete visual timers without altering double-click timing.

For an input failure that automated browser checks cannot reproduce, `npm run dev` exposes an opt-in `dragTrace` helper in the page's developer console. Refresh after changing the instrumentation, run `dragTrace.start()`, reproduce one failing gesture and one successful comparison, then run `copy(dragTrace.stop())` in Chrome's console. `dragTrace.json()` exports the same JSON without stopping; `start()` clears the previous recording. The trace records raw pointer/mouse events with browser timestamps and received times, coalesced movement samples, capture/focus/resize events, preview/release geometry, commit/cancellation reasons and snapshots of saved versus displayed positions. It buffers at most 4,000 entries in memory, reporting any discarded entries, and avoids per-move console output or forced geometry measurements. One post-release frame measures the resulting tile. A page unload saves the last recording in tab-local session storage so `json()`/`stop()` can retrieve it after a development reload. Recording never uploads data and is absent from production builds. Treat exported traces as disposable verification output under the retention policy below.

The encyclopedia book renderer is separate from standalone readings. Preserve its dialog and index DOM while selecting details; page visibility must update inertness and accessibility state along with the visual slide at every viewport width. Page-local headings and controls move within the same track as the index and reading, with the central fold separating them. Live text refresh must not commit a new interaction anchor or steal editor focus.

Partner hints combine strict legal actions with useful preparatory placements from the engine. Preparatory placements set an unsatisfied hotspot prerequisite of an unfinished recipe or goal; the shared planning closure checks whether missing ingredients/fittings can coexist on a remaining branch without requiring unrelated goals to be complete. Result eligibility is shared with recipe matching. The browser projects these useful drags into reciprocal hover hints and outgoing drag targets; it does not interpret recipes independently. Actual combinations retain strict ingredient, fitting and placement checks.

Keep script/test source boundaries explicit so archived snapshots cannot accidentally enter the active build.

## Live authoring boundary

The core engine accepts a `Story`, a `State` and game actions. It has no editor, storage, worker or text-buffer dependencies. Authoring is a browser adapter around that interface:

- `story-document.ts` resolves URLs and owns draft storage. `authoring.ts` coordinates the buffer, saved copies and explicit deletion. Raw input is written synchronously before parsing, linting or preview updates; neither game reset nor a parser failure can delete it. Independent tab records preserve concurrent copies, and failed writes retain an in-memory exportable buffer.
- `mobile-debug.ts` renders the compact chapter picker from chapter names and callbacks; it has no editor or engine dependency. The browser controller switches between that picker and the desktop editor at the responsive breakpoint. Hiding the editor preserves its buffer and desktop open preference.
- `editor.ts` owns the debug pane and its persistent CodeMirror view, mapped diagnostic decorations/list, selection and scroll. `editor-chapters.ts` supplies the caret-synchronized dropdown and source headings shared with checkpoint lightbulbs; both controls pass source lines to the browser controller's existing checkpoint path. The editor converts original CRLF offsets to CodeMirror's single-character line breaks before displaying diagnostics or related links. Gameplay rendering never replaces its subtree.
- `editor-search.ts` uses CodeMirror's public search-panel API, query cursor and navigation/replacement commands. Recount matches when the document or search terms change; selection-only updates use the existing match positions. Replacement transactions retain ordinary editor Undo and synchronous draft saving.
- `story/language-service.ts` exposes strongly typed `hover`, `definition` and `references` operations over an immutable document, following LSP operation semantics without JSON serialization or a server transport. Clients call the interface directly with UTF-16 offsets; reference requests may also retain a resolved identity so an open list survives edits. It reads the shared parser's authored reference provenance, including duplicate recipes, qualifiers and implicit uses. Keep syntax recognition and identity resolution out of the UI. `editor-language.ts` owns only CodeMirror hover/highlight, navigation and references-panel presentation. Cache by the exact buffer, and refresh open reference lists after the synchronous draft save, disabling stale links until the new snapshot is ready. An interpretation failure cannot block saving raw input. Gameplay continues to use the same parser and engine without requiring editor services.
- Semantic coloring uses the same typed service's `semanticTokens` spans for explicit references and parser-recognized author comments; implicit uses never color an entire source row. Map existing decorations during edits and refresh from the current buffer after raw-draft saving. `hover` returns a typed symbol-or-image result. The browser resolves preview artwork through `resolveStoryAsset` with the current manuscript base, retaining the player's URL restrictions and redirected/draft asset paths.
- `live-story.ts` turns partial parsed models into playable previews and reconciles state between manuscripts. It matches chapters and item declarations, preserves surviving placements/constructions, reevaluates changed goals and supplies an empty chapter when necessary. It uses shared engine operations for game semantics.
- `main.ts` keeps the last game-interaction anchor (source, state, chapter entry, reader and scroll position). Every edit projects from that anchor rather than committing the previous provisional preview. Restoring deleted text can therefore restore the corresponding position and constructions. A subsequent game interaction commits the displayed state. Edited snapshots are structurally checked on reload and keep a separate chapter-entry snapshot for restarting.
- `live-diagnostics.ts` runs deterministic checks after the short preview debounce and queues global analysis to `lint-worker.ts`. There is one worker and at most one newest pending buffer. Revisions invalidate old results immediately on input, before debouncing. Fast results replace fast diagnostics while retaining mapped deep diagnostics; complete results replace both. CodeMirror maps existing spans through each text transaction, so insertions/deletions do not clear the panel while work is pending.

Lint fixes contain source edits, not engine actions. The parser retains authored fate sites separately from deduplicated recipes so fixes cover duplicate declarations and shorthand inputs without changing recipe identity. Goal acknowledgments retain separate source metadata and never enter the goal or item registries. Implicit installation semantics constrain which fate fixes are possible. The editor converts offsets and line endings, disables stale actions and applies the complete edit set in one isolated Undo transaction through normal autosave. A fix can select a span within its inserted text, such as the reason placeholder. Source and checkpoint lightbulbs use zero-width inline CodeMirror anchors at their text endpoints and share the editor's action menu; diagnostic-list bulbs overlay the measured final text fragment. The browser controller resolves a checkpoint's source line and generates it through the shared checkpoint planner.

Draft persistence, diagnostics and preview state have separate failure paths. Keep saving the raw text even when interpretation fails. Browser partner hints report analysis limits without throwing out of pointer handlers. The CLI additionally checks local artwork files on disk and verifies authored hotspot destinations in Chromium; the browser supplies placement geometry from its prepared artwork. Avoid accumulating editor-specific exceptions in the deterministic engine. The [README](../README.md#edit-a-story-live) owns user-facing editing and recovery instructions.

## Verification records

Keep executable checks, reviewer instructions and concise final outcomes. Record scope, pass/fail, adopted fixes, failures that matter and remaining limits. Inputs and outputs of verification runs are temporary: copied source/runtime bundles, checkpoints, action histories, screenshots, geometry dumps, individual reviewer answers, logs and detailed reports belong in ignored `runs/` space while investigating. Discard them after recording the conclusion; do not commit or archive them, including in compressed form.

Source artwork, generation prompts, authoring geometry and explicitly requested contact-sheet PNGs are design deliverables. Curate them with their ongoing project: keep each distinct artistic statement, its verdict, enough reference material to recreate that direction, and worthwhile completed work. Discard intermediate exports, duplicate views and the minutiae of superseded attempts. Their existence does not require retaining the surrounding verification run.

During a run, bind observations to the actual tested version and use matching inputs for replay. A retained summary without the run details is an outcome record, not replayable evidence. The [README](../README.md#frozen-evidence-and-evaluation) describes temporary run artifacts; [fun and evaluation](fun-and-evaluation.md) governs what claims they support.
