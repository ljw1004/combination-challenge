# Engineering guide

This document owns implementation boundaries, technical constraints and testing policy. Game semantics belong to the [specification](story-format-spec.md), editorial choices to the [authoring guide](story-authoring.md), and commands to the [README](../README.md#tools).

## Boundaries

- Use one parser/model and one deterministic game core for the browser, linter, checkpoint planner and logical runner. Do not copy transition logic into individual clients.
- Story semantics stay in `src/engine/`; browser code owns geometry, pointer handling, dialogs and local storage. The engine retains finite move coordinates exactly; the browser constrains drops and new creations using measured tile bounds, rather than fixed text-card limits.
- Parsing preserves file/line provenance, section headings, declarations, qualifiers and explicit/default fate distinctions. Every diagnostic and related location has a UTF-16 text span into the original buffer, including CRLF offsets, as well as readable source locations. Related locations include explanatory messages, not just addresses.
- `Story.sourceReferences` retains authored declaration/use spans before recipe deduplication. Declaration lint and language-service navigation share this provenance, including forward references, explicit identities, chapter headings and presentation thresholds, and inherited shorthand. Chapter symbols resolve through the shared chapter-reference model; chapter IDs share the authored identifier namespace with items and hotspots. Resolve declaration requirements over the whole manuscript in fast lint; keep provisional parsed identities available to incomplete previews. Unresolved references prevent deep analysis, never raw-draft saving. Do not infer chapter supplies from declaration validation or add generated installation uses to the unused-declaration count.
- Node-only story discovery and file I/O live outside browser modules. The browser fetches ordinary Markdown and artwork files; Vite bundles application code and renders catalogue cards into the generated root `index.html`. The root `-dev.html` files remain the editable templates; the development middleware uses them instead of the generated HTML. Root builds must keep `emptyOutDir: false`; bundle cleanup is limited to obsolete files in the previous generated inventory. See the [loading routes](../README.md#run-the-game).
- Ordinary saves are versioned action histories bound to a story fingerprint. Replay reconstructs logical state; browser positions are presentation metadata. Edited previews need the separate snapshot boundary described below because changed rules cannot replay the old history faithfully.
- Item stacking is browser presentation metadata alongside positions: persist it in saves, interaction anchors and chapter-entry snapshots, and remap identities during live edits. Append new identities and raise picked-up items; feedback CSS must not override their order. See the [dragging contract](ux.md#work-surface-and-dragging).
- New-result placement uses the engine's computed receiver status after retention checks. Capture the receiving tile's rectangle before rendering removes it; then use measured result dimensions to centre a replacement or find adjacent space. Compound fitting updates the existing owner without applying new-result placement.
- Hotspot drop resolution lives in `engine/hotspot-drop.ts` and uses legal actions, actual occupants and the receiving chapter. Pointer preview and release use the same resolver. `place:` references do not enter the item registry. Shared hotspot markup, sizing and rectangle calculations serve gameplay and geometry lint; the CLI measures hotspot surfaces with Chromium for manuscripts containing placements, and both CLI and live editor also decode backgrounds for every authored centre or hitbox size. Upper-bound diagnostics require actual image dimensions, including for primitive starts without placements. The live editor measures declared placement surfaces at the reference width after preparing their artwork and backgrounds. Geometry measurements travel with the diagnostic revision into the worker.
- A successful authored result snap is recorded as `resultPlacement` on its combination action. The browser first resolves dispositions and measures the result, then replays that one action with the chosen placement so hotspot membership, goal latching and restoration remain engine-owned. Occupancy fallback leaves the normal action unchanged. The engine validates the destination's hotspot context, applicable authored entry and finite coordinates; browser geometry remains responsible for rectangle containment and collisions.
- Logical observations expose only normal player information. Keep unperformed recipes and raw checkpoint state out of fresh-player observations; render performed past actions as ordinary game history. The [playtest protocol](fun-and-evaluation.md#logical-playtesting) defines the runner's interface.
- The adventure layer translates shared engine transitions into public messages and choices for both terminal and AI players. Acknowledge cards internally before offering the next choice; stop AI chapter trials at their boundary. Validate the complete structured reply before mutation. A once-per-step look (`L` in fast mode, `{look:true}` in detailed mode), available after the chapter’s first gameplay action, redisplays the same board without an engine action; fold it into the following actual structured response as `lookedAgain`, preserving the refresh frame for replay rather than creating a separate action entry. Keep a pending flag across interruption/reload; do not consume or merge the prior result’s reflection during a refresh. Checkpoint history and looks remain outside gameplay counts. Freeze the canonical rubric document with source and the explicitly supplied additional guidance with the session; preserve that guidance unchanged in player and grading packets, and verify its hash as well as both public frames and engine replay, including checkpoint and automatic actions. Independent grade validation checks references, step coverage and arithmetic, never invents judgments of enjoyment. Freeze the explicitly selected fast/detailed mode with the session. Detailed inspections and unsuccessful well-formed combinations advance the decision ledger even when the engine state is unchanged. Name/protocol errors do not. `engine/logical-actions.ts` prepares, executes and clears detailed hotspot operations through ordinary engine actions; these replayable internal actions form one player decision. Keep recipe matching, required fittings, dispositions and goal latching in the shared engine, and keep terminal autocomplete independent of compatibility.
- Apply the [archive policy](../archive/README.md) when consulting historical implementations.

## State and continuation analysis

Token statuses record visibility and incorporation, while `State.excluded` records permanent exclusive choices. Hidden tokens remain in state. The browser encyclopedia derives distinct described identities from all current tokens, never only available tokens. Each token records immutable first-encounter chapter/order separately from its mutable placement chapter. Supplies and creations stamp the current progression chapter; moving, carrying, retiring and installing do not change it. Ordinary old saves reconstruct this metadata through replay. Edited snapshots retain/remap valid metadata; legacy edited history that cannot be safely reconstructed is explicitly grouped as earlier discoveries, not guessed from current placement. Chapter/story restoration restores inventory and encounter metadata together. Keep chapter progression, goal latching, slot installation and input hiding in the shared engine so browser and logical play agree.

Assess candidate hidden inputs jointly at the combination event. Do not independently approve two removals that together block progress, or retroactively hide retained inputs on unrelated actions or reload. Include every unfinished goal in each `next:` chain in continuation checks, even if the chain's final goal has already been achieved. Use the same complete-chain predicate for chapter completion and skipping; sequential display never waives a predecessor. These are implementation obligations for the specification's protection rules.

The analysis enumerates unresolved exclusive pairs, then computes reachable constructions with the chosen branch and chronological hotspot availability. It has an explicit limit of 12 unresolved exclusive pairs rather than silently claiming exhaustive analysis after truncation. This is an implementation of the specified retention model, not an independent formal proof of its invariant.

Deep lint uses this same closure to identify blocked goals on failing branches and reports at those requirements, rather than the story title. Do not infer that each conflicting goal is individually impossible. Structural counts and a replayed completion route belong in the shared analyzer; chapter arrival and peak counts must use the shared engine's actual boards.

The separate content-opportunity linter plans sets of goal/target dependencies backwards, deduplicating constructed identities and installed slots before combining independent goals. It evaluates each set with one working state through the shared engine; it does not enumerate partial action subsets. Chapter histories store independent OPTIONAL records and collapse pessimistically without expansion. Retirement is assessed against the completed construction set, rather than inherited from a representative playthrough. Histories with the same available inventory can merge retired-versus-uncreated intermediates. Keep their possible noncreation separately from creation blockers: losing future alternatives must not accidentally give another ingredient extra cleanup protection. The engine's optional retirement-check callback supports this abstract query while ordinary gameplay retains its default continuation policy. Explanations describe observed blockers and source rules; they must not change analysis outcomes. The [lint specification](story-format-spec.md#opportunities-for-authored-content) owns the calculation and its deliberate losses. Stop above 100 distinct alternatives and report an analysis-limit error without unreachable-item findings. Keep small, explicit gameplay counterexamples as regression fixtures. Statistics must distinguish construction-set evaluations, engine operations and maximum family width.

## Tests that earn their cost

The full default suite should finish in about 20 seconds. It includes semantic tests and Chromium interaction checks. Keep cases small and purposeful: parsing ambiguity, jointly hiding inputs, exclusive branches, compound preservation/wrapping, goal latching, hidden-information boundaries, real drag/reload/reset, and one complete legal witness for each active story.

Do not snapshot whole stories, pin incidental counts or rerun historical tests. A change in wording is not a reason to rebuild a large expected-output fixture. Add a regression case when a real counterexample exposes an important semantic boundary. Compare semantic state rather than string snapshots of large UI markup. Run timing checks when new tests or code make them relevant. Archive hash verification is an occasional preservation check, not part of each development test run.

Match verification to the change. Engine and browser work uses relevant automated tests and the application build; it does not require running manuscript-wide lint or story analysis. Story validation is a separate step for changed manuscripts or artwork, or an explicitly requested audit. The [publication workflow](../README.md#github-pages-publication) owns the commands and preparation steps for each kind of change.

Story projects use the shared linter, analyzer and development server. Keep drag, reload, layout and draft-loading checks in the general browser suite, rather than maintaining a verifier or Vite configuration for each manuscript. A story-specific failure should become a small shared regression case when it exposes an engine defect.

## Browser implementation

`home-screen.ts` owns home-screen metadata and standalone-window detection. Build a `data:application/manifest+json` link in the page with absolute `id`, `start_url`, `scope` and icon URLs: a data URL supplies no directory for relative references. Reuse the existing image URL, reporting its decoded intrinsic dimensions rather than claiming unprovided icon sizes or maskable artwork. Metadata preparation must not block story loading or play, and an obsolete image decode must never replace a newer identity. Supply Apple touch-icon/title tags and application-name metadata alongside the manifest, leaving the shared tab title/favicon intact. Identify story apps by the resolved manuscript URL; identify the catalogue by its canonical `index.html` URL. Use the hosting directory as the navigation scope, including when deployed beneath a subdirectory. Story launch URLs retain the manuscript selection but omit the Home flag and transient page state. Catalogue navigation carries `home=show` only from the current standalone window; do not use origin-wide local storage to infer installation context. The [home-screen UX](ux.md#home-screen-apps) owns the visible behaviour.

Story-heading artwork stays ordinary Markdown. The parser retains its authored heading, image source spans and separate text title; catalogue rendering resolves those images beside the manuscript and uses the shared display size in [UX](ux.md#catalogue-and-story-identity). The HTML transform embeds `src/web/style.css` in the catalogue during development and production, keeping one editable CSS source without a separate catalogue stylesheet request. `artwork-browser.ts` reuses Chromium for CLI heading-image dimensions and optional placement geometry. Live authoring loads heading images only when diagnostics are active and sends their measured dimensions with the matching revision to the lint worker. Both callers use `storyIconDiagnostics`; missing or invalid identity artwork must not suppress independent logical reachability analysis or block provisional editing.

Conditional hotspot artwork resolves in `engine/presentation.ts` from retained tokens and fitted contents, independently of availability. Preserve source order within each chapter presentation; scene inheritance reuses that presentation. Keep these references out of chapter needs and continuation analysis. Artwork planning projects the next recipe's creation/fitting effects to preload affected hotspots, including scrollback, without replaying the whole transition for each speculative image. Geometry probes measure every declared icon variant and applicable fallback with its own dimensions; carry the variant index through CLI and live-editor measurement. The specification owns the syntax and UX owns visible behavior.

`artwork-plan.ts` selects cover/current-scene requirements, immediate legal combination results and the next chapter's new primitive supplies and changed carried-item icons through the shared engine. The shared presentation resolver selects names and icons independently for a progression chapter; browser rendering, artwork planning and human/AI text play use that resolver. Do not use the complete item registry as a preload list. `artwork-loader.ts` owns a four-request queue, required-before-speculative priority, URL deduplication, decoded-image dimensions, cancellation and bounded retries (250ms/1s backoff, an 8s attempt timeout and a 30s cooldown after exhaustion). Connectivity restoration permits failed entries to retry immediately. `item-artwork.ts` renders from that cache. The browser waits for only the layout it is about to display, and verifies that its source/state still match before applying an action delayed by artwork. Keep resize callbacks behind the initial preparation gate. The [artwork UX contract](ux.md#artwork-loading) owns the preload horizon and visible waiting/fallback behavior.

The story cover is a presentation gate, not an engine action. Unstarted covers do not persist game progress; Start captures the ordinary arrival state, while valid existing saves and explicit debug checkpoints bypass the gate. Pre-start live edits regenerate a fresh initial game rather than reconciling inventory the player has never seen. Story restart removes only that story’s progress before returning to its cover; chapter restart restores its existing arrival snapshot and popup.

Cover and chapter rendering share viewport geometry. Use a 390-unit-wide scene whose height follows the decoded background aspect ratio (390 × 844 for standard phone art). Stored positions use scene units; authored centres and receiving boxes remain in actual background-image pixels in the parsed model. Convert them through the decoded background dimensions only at the rendering boundary; never treat authored pixels as CSS pixels or as fractions. Automatic placement may still use internal ratios. Fixed replacements retain the authored pixel centre, or an explicitly tagged automatic anchor, independently of receiving rectangles. Apply the [UX framing rule](ux.md#work-surface-and-dragging) independently to each chapter, keeping its scenery, items and targets on the same uniform transform. Measure visible bounds for drops and result placement; when dragging across chapters, convert through each scene’s own transform. Clip the world's transformed overflow so it cannot extend the scroll range. Chapter offsets use the available viewport height, not the reference image height. Save the viewport height with scroll anchors and normalize them on restoration. During resize, retain the last deliberate scroll position before browser layout clamps it; incidental resize scroll events must not become authoring interaction anchors.

Scenery and the interactive board use separate stacking contexts with the same scene geometry and scroll container. Place fixed goals between those layers and the debug control above the board but below reading dialogs; use native paint order and hit testing instead of clipping holes around items. Transparent board space passes input through to uncovered goals, while items and hotspots retain their own hit areas. During dragging, the debug control passes pointer input through without changing its paint order or opacity. Preserve background image nodes when moving from the cover to the first chapter and during reconciliation.

Arrival layout is a browser-only geometry operation shared by icons and text cards. Capture each retained token's placement chapter before advancing the engine, independently of its immutable encounter metadata. Pass measured visible bounds, goals, item sizes, transient badge headroom and hotspot shapes to the layout; capture the completed arrangement in the chapter-entry snapshot. `icon-names.ts` measures hidden badges once per render, reserves their headroom for automatic creation and uses cached dimensions to keep badges inside the scene during movement. The layout packs image-and-badge footprints, then returns image coordinates, preserving authored centres and inherited occupants. Retry failed groups as complete arrangements as spatial preferences yield; hotspot overlap in these coordinates must never mutate logical membership or dispatch an engine action. A carried badge already visible inside the top comfort margin does not displace its settled image. Circular hotspot pointer targets, clearance, overlap scoring and placement lint share the inscribed-circle geometry with the minimum touch diameter. The [UX arrival contract](ux.md#chapter-arrival-layout) owns ordering, reservations and exceptions.

An explicit hotspot receiving rectangle changes the outer hotspot DOM box, while its image stack retains the original artwork centre and quarter-size dimensions through a visual offset. Pointer handling, drop resolution, names, creation placement, arrival clearance and the browser placement probe therefore share the same measured receiver. Invalid live hitbox metadata falls back to ordinary geometry; it never changes logical recipes or fixed-item counting. Keep the icon stack pointer-transparent when it extends beyond its owner.

Tutorial markers retain authored source/chapter provenance separately from deduplicated recipes. Count/chapter checks run in fast lint; first-move readiness uses shared engine recipe matching in deep lint. The browser uses that same directed action, with a separate decorative overlay and per-manuscript completion store. Cloned visuals carry no game identities or focus targets. The engine discovers two-item hotspot tutorial opportunities from current ingredients, fittings, result eligibility and normal hotspot drop resolution, including a hypothetical preparatory placement. The browser verifies the demonstrated next drop against measured targets. Keep opportunity selection stable while valid, and select visible cues by the priority in UX. Only actual accepted combinations and deliberate goals activations record accomplishments; checkpoint generation is not tutorial evidence. The [UX tutorial contract](ux.md#contextual-tutorials) owns sequencing, persistence and reset behavior.

Implement the interaction contract in [UX](ux.md). Preserve connected image and scene DOM nodes rather than replacing the world after each move; do not rewrite unchanged image URLs. Suppress native HTML drag, own pointer timers and capture through completion, cancellation, focus loss and resize, and measure long labels as well as simple physical-item names. Test real pointer events, and distinguish browser touch emulation from a native-device test.

The stable game container owns pointer capture; item reconciliation must not cancel an otherwise active drag. Capture loss with no buttons held can precede `pointerup`; retain the gesture for the document release handler instead of treating that ordering as cancellation. Capture loss while still pressed, `pointercancel`, focus loss and resize retain their cancellation paths. Preview and release share measured destination geometry, retaining the pickup offset and resolving the final rectangle directly from release coordinates before restoring visuals. The browser drop resolver projects engine legal actions and useful placement hints onto the eligible geometry; cache those choices only for the current gesture and keep target geometry live through scrolling. Hover replacement cancels obsolete visual timers without altering double-click timing.

For an input failure that automated browser checks cannot reproduce, `npm run dev` exposes an opt-in `dragTrace` helper in the page's developer console. Refresh after changing the instrumentation, run `dragTrace.start()`, reproduce one failing gesture and one successful comparison, then run `copy(dragTrace.stop())` in Chrome's console. `dragTrace.json()` exports the same JSON without stopping; `start()` clears the previous recording. The trace records raw pointer/mouse events with browser timestamps and received times, coalesced movement samples, capture/focus/resize events, preview/release geometry, commit/cancellation reasons and snapshots of saved versus displayed positions. It buffers at most 4,000 entries in memory, reporting any discarded entries, and avoids per-move console output or forced geometry measurements. One post-release frame measures the resulting tile. A page unload saves the last recording in tab-local session storage so `json()`/`stop()` can retrieve it after a development reload. Recording never uploads data and is absent from production builds. Treat exported traces as disposable verification output under the retention policy below.

The encyclopedia book renderer is separate from standalone readings. Preserve its dialog and index DOM while selecting details; page visibility must update inertness and accessibility state along with the responsive layout. CSS owns the available-width breakpoint; use the same resolved mode for controls, focus and Escape behavior. Page-local headings and controls move within the same track as the index and reading, with the central fold separating them. Store displayed-wonder and selection history with browser progress, separately from engine discovery acknowledgments; remap its identities with authoring anchors. Live text refresh must not commit a new interaction anchor or steal editor focus.

Partner hints combine strict legal actions with useful preparatory placements from the engine. Preparatory placements set an unsatisfied hotspot prerequisite of an unfinished recipe or goal; the shared planning closure checks whether missing ingredients/fittings can coexist on a remaining branch without requiring unrelated goals to be complete. Result eligibility is shared with recipe matching. The browser projects these useful drags into reciprocal hover hints and outgoing drag targets; it does not interpret recipes independently. Logical observations project the same sources into combination and placement actions, using the shared hotspot-drop resolver for occupied-target priority and visited chapter surfaces. Neither projection exposes recipe results. Actual combinations retain strict ingredient, fitting and placement checks.

Keep script/test source boundaries explicit so archived snapshots cannot accidentally enter the active build.

## Live authoring boundary

The core engine accepts a `Story`, a `State` and game actions. It has no editor, storage, worker or text-buffer dependencies. Authoring is a browser adapter around that interface:

- `story-document.ts` resolves URLs and owns draft storage. `authoring.ts` coordinates the buffer, saved copies and explicit deletion. Raw input is written synchronously before parsing, linting or preview updates; neither game reset nor a parser failure can delete it. Independent tab records preserve concurrent copies, and failed writes retain an in-memory exportable buffer.
- `mobile-debug.ts` renders the compact chapter picker from chapter names and callbacks; it has no editor or engine dependency. The browser controller switches between that picker and the desktop editor at the responsive breakpoint. Hiding the editor preserves its buffer and desktop open preference.
- `editor.ts` owns the debug pane and its persistent CodeMirror view, mapped diagnostic decorations/list, selection and scroll. `editor-chapters.ts` supplies the caret-synchronized dropdown and source headings shared with checkpoint lightbulbs; both controls pass source lines to the browser controller's existing checkpoint path. The editor converts original CRLF offsets to CodeMirror's single-character line breaks before displaying diagnostics or related links. Gameplay rendering never replaces its subtree.
- `editor-search.ts` uses CodeMirror's public search-panel API, query cursor and navigation/replacement commands. Recount matches when the document or search terms change; selection-only updates use the existing match positions. Replacement transactions retain ordinary editor Undo and synchronous draft saving.
- `story/language-service.ts` exposes strongly typed `hover`, `definition` and `references` operations over an immutable document, following LSP operation semantics without JSON serialization or a server transport. Clients call the interface directly with UTF-16 offsets; reference requests may also retain a resolved identity so an open list survives edits. It reads the shared parser's authored reference provenance, including duplicate recipes, qualifiers and implicit uses. Keep syntax recognition and identity resolution out of the UI. `editor-language.ts` owns only CodeMirror hover/highlight, navigation and references-panel presentation. Cache by the exact buffer, and refresh open reference lists after the synchronous draft save, disabling stale links until the new snapshot is ready. An interpretation failure cannot block saving raw input. Gameplay continues to use the same parser and engine without requiring editor services.
- Semantic coloring uses the same typed service's `semanticTokens` spans for explicit references and parser-recognized author comments; implicit uses never color an entire source row. Map existing decorations during edits and refresh from the current buffer after raw-draft saving. `hover` returns a typed symbol-or-image result. The browser resolves preview artwork through `resolveStoryAsset` with the current manuscript base, retaining the player's URL restrictions and redirected/draft asset paths.
- `live-story.ts` turns partial parsed models into playable previews and reconciles state between manuscripts. It matches chapters and item declarations, preserves surviving placements/constructions, reevaluates changed goals and supplies an empty chapter when necessary. It uses shared engine operations for game semantics.
- `main.ts` keeps the last game-interaction anchor (source, state, chapter entry, reader and scroll position). Every edit projects from that anchor rather than committing the previous provisional preview. Restoring deleted text can therefore restore the corresponding position and constructions. A subsequent game interaction commits the displayed state. Edited snapshots are structurally checked on reload and keep a separate chapter-entry snapshot for restarting.
- `live-diagnostics.ts` starts with the desktop editor, runs deterministic checks after the short preview debounce and queues global analysis to `lint-worker.ts`. There is one lazily created worker and at most one newest pending buffer. Placement geometry prepares only hotspot icons with authored placements; item icons are not required for that analysis. Revisions invalidate old results immediately on input, before debouncing. Fast results replace fast diagnostics while retaining mapped deep diagnostics; complete results replace both. CodeMirror maps existing spans through each text transaction, so insertions/deletions do not clear the panel while work is pending.

Lint fixes contain source edits, not engine actions. The parser retains authored fate sites separately from deduplicated recipes so fixes cover duplicate declarations and shorthand inputs without changing recipe identity. Goal and hotspot acknowledgments retain separate source metadata and never enter the goal, hotspot or item registries. Count active hotspots through the shared scene-inheritance function. Implicit installation semantics constrain which fate fixes are possible. The editor converts offsets and line endings, disables stale actions and applies the complete edit set in one isolated Undo transaction through normal autosave. A fix can select a span within its inserted text, such as the reason placeholder. Source and checkpoint lightbulbs use zero-width inline CodeMirror anchors at their text endpoints and share the editor's action menu; diagnostic-list bulbs overlay the measured final text fragment. The browser controller resolves a checkpoint's source line and generates it through the shared checkpoint planner.

Draft persistence, diagnostics and preview state have separate failure paths. Keep saving the raw text even when interpretation fails. Browser partner hints report analysis limits without throwing out of pointer handlers. The CLI additionally checks local artwork files on disk and verifies authored hotspot destinations in Chromium; the browser supplies placement geometry from its prepared artwork. Avoid accumulating editor-specific exceptions in the deterministic engine. The [README](../README.md#edit-a-story-live) owns user-facing editing and recovery instructions.

## Verification records

Keep executable checks, reviewer instructions and concise final outcomes. Record scope, pass/fail, adopted fixes, failures that matter and remaining limits. Inputs and outputs of verification runs are temporary: copied source/runtime bundles, checkpoints, action histories, screenshots, geometry dumps, individual reviewer answers, logs and detailed reports belong in ignored `runs/` space while investigating. Discard them after recording the conclusion; do not commit or archive them, including in compressed form.

The explicitly requested [fun-playtest deliverables](fun-and-evaluation.md#run-files) are an exception: retain each chapter's structured player-response arrays and report, plus the mechanically assembled whole-playtest report, in the timestamped project playtest directory. Keep source/runtime bundles, packets and intermediate grading files temporary. These selected deliverables do not constitute a replayable session.

Trial image generations, rejected candidates, reference crops, intermediate exports, lifecycle sheets and browser/assembly proofs are disposable scratch under ignored `runs/` by default. Do not check them in or copy every generated image into a study. Build review panels from existing artwork when possible. Remove disposable files after retaining the useful decision and concise outcome; do not treat `runs/` as a permanent archive.

Selected production masters, their exact requests and necessary reference inputs, authoring geometry and final runtime assets are design deliverables. Promote only the selected material into the active project, with runtime assets beside the manuscript and without redundant production copies. Retain a rejected example only when it is deliberately selected as a useful design reference, with its reason recorded; a small representative example can preserve the lesson without the whole attempt history. Explicitly requested art and contact sheets are also retained deliverables. Frozen references requested by the user remain preserved. These exceptions do not justify retaining the surrounding verification run. A generation tool's own cache follows its applicable cleanup permissions separately.

User-supplied inspiration photographs, artwork and selected style references are retained design material even if they are not generation inputs or do not appear in the final result. Preserve the original files and their known provenance in an indexed project `inspiration/` or reference collection. Temporary crops, downloads for general research and inspection sheets remain subject to the scratch policy above. Follow the [archive policy](../archive/README.md#project-evidence) when consolidating completed work.

During a run, bind observations to the actual tested version and use matching inputs for replay. A retained summary without the run details is an outcome record, not replayable evidence. The [evaluation guide](fun-and-evaluation.md#frozen-evidence-and-evaluation) describes temporary run artifacts; [fun and evaluation](fun-and-evaluation.md) governs what claims they support.
