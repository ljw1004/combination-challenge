# Find the game before its interface

25 October 2026. The owner's correction is the current priority: work wholly in logical game space. Browser/UI implementation and testing are frozen. The existing screens are past experiments, not evidence selecting a game. Current candidates use pure TypeScript models, public JSON observations and abstract `combine` actions.

The preserved constraints are inspectable legal combinations, inexhaustible concepts, and a challenge beyond guessing the author's ontology. No material inventory, action-credit allowance or query score is introduced. A diagnostic player allowance is a test stopping rule, never a loss rule inside a game.

**Latest owner clarification:** narrative must emerge from the game's primitives, with little written story. Terrain, time, processes, avatars and foes can express it through their actual behavior. Combining onto a place is promising: the place may act as a persistent catalyst in A+B at P. The same availability highlights should apply to places. Continue testing logical laws first, with state and transitions that can be expressed through game objects; authored dialogue and chapter queues are superseded as the current direction. [Current contract](design-contract.md#current-correction-the-world-carries-its-history).

## The actual loop

1. Name the skill or experience the candidate might provide and an observation that could contradict it.
2. Implement a tiny deterministic state/action model with a public observation boundary.
3. Check reachability, purity and simple counterexamples. Keep privileged model search separate from player evidence.
4. Give a fresh agent only the logical command interface. Record predictions, exact actions, responses and conditions; replay every run.
5. Inspect the actual inference, equivalent work and alternatives. Revise one structural factor and test again. Return to original designer arguments when interpreting the result.

The player command is `node experiments/logical-play.ts`. `list` gives games/scenarios; `init ID GAME SCENARIO SEED CONDITION` starts a session; `view ID` shows public state; `act ID 'JSON_ACTION' 'JSON_PREDICTION'` commits a combination. Exact immediate previews exist only where the game's rules expose them. Laboratory observations cannot be obtained by calling preview instead of performing the experiment. Players are instructed not to inspect source, saved runs or other sessions. Isolation is by instruction, not a security sandbox.

`npm run evaluate-logic` replays captures and records design judgments without a fun total. Raw games live in `results/logical-players`; human-readable reports identify fresh versus experienced conditions. No mouse, screenshot, animation, layout or browser metric participates.

## Return to designers after these traces

Reopened the original texts during this logical-only pass; their claims are hypotheses and design experience, not validated equations of enjoyment.

Daniel Cook's [The Chemistry of Game Design](https://www.gamedeveloper.com/design/the-chemistry-of-game-design), especially skill atoms, active skills, burnout and pre-existing skills, describes action/simulation/feedback/model updating, and learning that supports another useful skill. It also distinguishes missing prerequisites from skills already mastered before play. **Our inference:** test what a player learns or reinterprets, rather than count combinations. A highly trained language model recognizing a familiar Boolean factorization may say more about its starting expertise than about a human's likely difficulty. A reported wish to stop is agent evidence; do not label it measured human burnout. Nor does a learned action become a chore merely because it recurs in a new problem.

Arvi Teikari's [Baba Is You interview](https://www.gamedeveloper.com/design/designing-i-baba-is-you-i-s-delightfully-innovative-rule-writing-system), in the answer about brainstorming levels around words, describes finding interactions, constructing levels to require them, using tester alternatives for variants, and cutting ideas needing excessive supporting rules. **Our inference:** the next revision should change a useful relationship within the same two operators. A large catalogue, more variables or exceptions added to save a weak premise would be poor evidence. A specific intended insight can be worthwhile; demanding multiple equally good solutions everywhere would misread this design approach.

Cook also argues that mechanics alone omit the evolving player. That is compatible with the owner's request: abstract playtests still include a player making predictions and responding to consequences. The logical model is the fast testbed, not a declaration that mathematical complexity equals fun. These AI samples remain highly correlated and do not validate prediction of human enjoyment.

## Next structural revision, specified before play

Keep four independent inputs, all sixteen public cases, persistent concepts and ALL/EITHER. Change the required relationships: alternative complete coalitions; one essential anchor with direct or joint support; and support through neighboring links. Do not merely rename columns or add more variables.

Hypothesis: changing which roles must work together produces another composition insight, while shorter constructions reduce execution after a settled plan. Counterevidence would be direct reuse of the same formula under renaming, a player deriving everything before the first move and describing all remaining actions as clerical, or a changed name concealing an identical relation. Fewer combinations alone is not success; difficulty and pleasure need not rise together. This tests a small puzzle sequence, not civilization simulation or a causal account of real institutions.

All completed runs must remain exactly replayable. A temporary state-schema refactor added a title field to relations-1 and broke hashes; the original state shape/order was restored and all three captures replay without alteration. Relations-2 is a separate model. Publicly unchanged behavior does not authorize silently rewriting recorded evidence.

## Executed revision and progression

Relations-2 genuinely changes the formulas: alternative complete coalitions, an essential anchor with substitute support, and neighboring support links. Exact witnesses and the experienced player each use3,3,4 combinations. Renaming/duality checks distinguish the functions; each fixed witness solves only its own context. However, the player found every construction before committing the first action. It noted that the goal prose substantially suggested the decomposition. A general minimal-sufficient-set method solves all three; this is an adaptive method rather than one fixed expression, but it can make these small cases worksheets for an expert. [Revision report](../results/logical-players/logic-rule2-report.md).

The next version tests actual persistence over those same sixteen possible worlds. It gives all required case constraints without the target-decomposition prose. All three goals are public, and a completed stage opens the next while retaining every established condition. An already-known future answer satisfies its stage automatically. There are still no inventories, scores, gate limits or deadlines. The model is [logical-progression.ts](../experiments/logical-progression.ts), available as `progression sequence` in the public CLI.

A genuinely fresh player completes the three stages in six commitments. It constructs the first condition in three, filters that whole result with A to satisfy the second in one, then combines a new BC relation with the retained first result to satisfy the third in two. It reports reuse of the whole previous result as the strongest moment. That is a concrete capability serving a subsequent inference; rebuilding the original chain is unnecessary. It also reports that most execution becomes routine after recognizing the minimal pairs, and would try one structurally different problem, not renamed repetitions. [Progression report](../results/logical-players/logic-progress-report.md).

**Decision:** retain reusable constructed relationships as the most promising narrow result of this pass. Do not promote the truth-table exercises to a finished game. The progression changes persistence and the observation condition while using a different fresh player, so it does not isolate a causal effect of either change. Upfront insight can be worthwhile; absence of plan revision is not a universal failure criterion. We still need a logical problem family that provides interesting new uses rather than recurring transcription. No return to UI is warranted by these results.

## Evidence audit

Nine sessions by three agent players contain43 committed combinations: three fresh sessions and six experienced follow-ups. All nine replay to their recorded outcomes. [Evaluation](../results/logical-evaluation.json) keeps outcomes, invalid attempts, annotations, access conditions, counterevidence and design decisions separate. [Player conditions](../results/logical-player-conditions.json) record the correlated model sample and remaining limits. Fifteen focused model/replay checks cover public information boundaries, immutable previews, exact saved replays and progression without recrafting.

The original command interface failed to log preview calls. The progression player reports one preview; the others report none. Treat that as self-report, not measured telemetry. Future logical-cli-2 runs record every preview with its decision index and result; existing captures/hashes remain untouched. Natural-language predictions are retained but not automatically scored as correct. No source claim, success count or AI preference establishes human enjoyment.
