# Current UX decisions

This is the authoritative record of the interface contract: interaction, presentation behaviour, navigation, accessibility, tutorials, editing and recovery. It describes the intended experience and includes motivations where known. Game syntax and semantics belong to the [Markdown specification](story-format-spec.md); content-writing guidance belongs to the [authoring guide](story-authoring.md). Reusable artwork methods belong in the [icon guide](icon-guide.md); durable intent for an individual story belongs in its `design-brief.md`. Research and construction history belong in the relevant project. Link to those rules rather than maintaining competing definitions here.

## Maintaining this document

- Update this document in the same change whenever a UX decision is adopted, revised or removed, including decisions made in conversation. Record small interaction details and failure/recovery behavior as well as major screens. A decision does not need a code change to belong here.
- State the latest decision directly in its relevant section. Replace or remove superseded text and reconcile any affected sections; do not append a dated amendment, keep rejected alternatives, or accumulate contradictory rules. Organize by the experience, not by implementation date or commit.
- Accompany a decision with its known motivation when it helps explain the tradeoff. Do not invent a rationale or turn an assumption into evidence of comprehension or enjoyment. Unknown motivation can remain unstated.
- Put chronology, commit references, research provenance, implementation/validation records and evidence limits in [working notes](../notes.md) or the [archive](../archive/README.md). Put unresolved proposals and evaluation work in the [backlog](../projects/backlog.md). None belongs here as a historical log.
- Consult this document before changing UX and check the final change against it. An implementation discrepancy does not silently supersede an agreed decision: fix the discrepancy or track it in the backlog. Other documents may explain usage or implementation, but should link here for the current UX contract.

## Overall presentation

Let the [game's philosophy](../README.md#philosophy) guide player and authoring UX.

Use a warm paper palette, outlined cards, square hotspot frames, high-contrast partner/drop states, reading dialogs and explicit chapter arrows. Keep scene artwork visible and leave natural working space for the objects. The interface should support recognizing, trying and discovering combinations without requiring an instructional screen or administrative steps. The [experience criteria](fun-and-evaluation.md) govern claims about whether that succeeds.

## Catalogue and story identity

Each story's ordinary Markdown H1 contains its identifying image and title. Render its heading images at **64 × 64 CSS pixels**, inline in their authored position with the image's bottom edge on the adjoining text baseline, regardless of source resolution. Allow ordinary text wrapping, rather than creating a separate image column. Put the description below the heading across the card's width. Preserve each image's authored transparency or opaque background, the shared cream surface and quiet card border; the artwork and prose carry each story's character. This keeps authoring in ordinary Markdown while leaving sizing to shared CSS. Include the catalogue's CSS in its HTML so rendering needs no separate stylesheet request or JavaScript. In the combined catalogue, story headings sit beneath the page's main heading. The [specification](story-format-spec.md#specification) owns the required square-image rule. Missing or invalid artwork remains editable and does not prevent provisional story play.

- Use **Make Something Worthwhile** as the catalogue's sole heading, with that capitalization and no final period or separate eyebrow title. Use the same name in the catalogue and player browser tabs, aligning the entry pages with the game's philosophy. The former player-page URLs are removed without redirects; the [README](../README.md#run-the-game) owns current route names.
- Use the simple gold-and-ivory mosaic sun on a full teal square as the shared site identity and favicon on the catalogue and player pages, and as the catalogue's home-screen icon. Its assembled ceramic and glass pieces express making a worthwhile whole from separate parts. The root `icon.png` is an opaque 256 × 256 export with straight square corners; retain the selected full-resolution master for future app uses. The authored background avoids a circular badge inside the platform's white home-screen tile. Individually pinned stories use their own home-screen identity below.
- Keep the story catalogue outside the game, on its own vertically scrollable page. Include its cards in the delivered HTML so the catalogue appears without a separate data request. Present each manuscript using its authored title and rendered description, including authored images and emphasis. The story's explicit background is used for the cover and excluded from the catalogue description, allowing independent artwork for these two settings. Ordinary description images remain catalogue content, including the first image. The [specification](story-format-spec.md#specification) owns declaration syntax and placement. Filenames, folder names, inventory counts and debugging metadata are not player-facing story labels. The manuscript's directory supplies the base for all its relative artwork.
- Resolve `make-something.html?story=PATH` relative to that HTML page, without adding a `stories/` prefix. Resolve relative artwork beside the resulting manuscript URL. Catalogue links use explicit `stories/...` paths beneath the root player page, matching development and publication without parent-directory traversal or copied stories. Development serves the editable `-dev.html` templates at the normal page URLs and regenerates the catalogue on reload. The shared development server also serves project drafts at their repository paths, so authors can preview them without a separate server or adding them to the published catalogue.
- Open each story at its own URL. A missing manuscript shows a visible load error with **Try again**; an unknown catalogue hash bookmark shows an explicit unknown-story error. Do not silently substitute another story. The [README](../README.md#run-the-game) owns route syntax and deployment layout.
- Identify browser progress, drafts and tutorial completion by the resolved full manuscript URL. Player routes that resolve to the same manuscript share that state; different manuscripts remain independent even when they share an artwork directory. A changed website origin or manuscript path has a separate identity; do not treat filenames as display titles or silently move saved data between stories.

## Home-screen apps

- In standalone WebKit apps, supply the system `Canvas` colour for a solid status-bar background, following the device's light/dark preference. This addresses the unwanted iOS fade over scenery while keeping the clock and system indicators visible. Apply the treatment to both catalogue and player, including loading/error views. The colour source must not paint over artwork, intercept input or add layout height. Let iOS size its status area and keep controls aligned to the current safe-area insets on rotation; ordinary browser tabs retain their existing appearance.
- Adding the catalogue (`/` or `index.html` beneath the site's hosting directory) to a mobile home screen suggests **Make Something** and the existing root `icon.png`. Adding a story suggests its parsed heading title and first heading image, resolved beside its manuscript. Keep the browser-tab title and favicon described above. These are installation suggestions; the browser and user control the final installed label and appearance.
- Use the currently loaded manuscript, including a saved or live-edited draft, for the story's installation metadata. Use the same artwork file for each identity's ordinary display and home-screen icon; do not add a separate home-screen artwork field or generate icon copies or separate manifest files. Creation uses its opaque square mosaic in both the catalogue and home-screen suggestion, extending the picture to every edge to avoid the white surround seen around its former circular silhouette. Other stories retain their authored silhouettes. Keep artwork corners square and let the platform supply its home-screen mask. The specification already requires square heading artwork; an incomplete draft with no usable icon remains playable without a substitute install icon or manifest.
- When the catalogue runs in standalone mode, add `home=show` to its story links, including legacy hash-bookmark navigation. Normal browser catalogue links stay unchanged. The catalogue itself needs no launch parameter or persistent installation flag.
- Show a quiet house-outline link at the player's top left only when both standalone mode and `home=show` are present. It returns to the catalogue. Match the bug control's subtle colour, 22px glyph, 44px touch target and scene-frame/safe-area alignment; give it the accessible name **Home** and apply the shared [focus rule](#work-surface-and-dragging). Keep it above scenery and objects, below reading dialogs, and visible while passing pointer input through during dragging. Keep it available on covers and loading/error views as well as during play, so catalogue users can always get back.
- Preserve the navigation flag through story reloads, and update the link/control if the current window's display mode changes. Directly opened or individually pinned stories have no Home link; an ordinary browser tab with a copied `home=show` URL also has none. A story's installation launch URL omits the flag, so pinning that story separately does not pin the catalogue navigation context with it.
- Returning Home preserves progress and drafts. The flag never participates in manuscript identity, saves, tutorials or app identity. Two separately pinned stories retain distinct installation identities even when their titles match.

## Artwork loading

- Present **Loading story…** as plain, static dark text centered horizontally and vertically on a cream background filling the game pane, matching the catalogue palette. Keep this first impression quiet: no panel, icon, spinner or animation. Include the loading view and its essential styling in the initial HTML so it is present before the application JavaScript loads, and replace it as soon as the opening view is ready without adding a minimum display duration.
- For a fresh story, **Loading story…** lasts only through manuscript preparation and loading/decoding the cover (or the first background when no cover is declared). Item dimensions are not needed for a cover. Restoring saved progress waits only for the current chapter's visible artwork and immediate reading, with scrollback prepared afterward. Resizing must not reveal an unprepared opening view.
- While the cover is visible, preload the first chapter's starting artwork. During play, preload only artwork one available combination away, including its fitted overlays and applicable discovery illustrations. Refresh that set after actions; do not recursively follow the recipe graph. Each chapter also preloads the next chapter's background, hotspots, new primitive supplies, changed icons for carried items and introductory illustrations. Use the current game's supply and combination rules, including exclusions and already completed chapter skips. Resolve item artwork using the chapter being prepared; scrollback uses the current progression chapter and loads its revised artwork after the current view is ready. Unrelated future artwork must not compete with the current view or spend the player's cellular data in advance.
- Visible artwork takes priority over speculative work. Keep downloads bounded, reuse successful loads and cancel obsolete lookahead. Retry intermittent failures with bounded backoff; an exhausted failure keeps readable item/hotspot fallbacks and remains eligible for a later retry, including when connectivity returns.
- If Start, a combination or a chapter jump outruns its preload, retain the current view until the needed artwork has dimensions or reaches its failure fallback. Pause game actions during that wait, showing **Loading artwork…** when it lasts long enough to be noticeable. Editing or another explicit checkpoint invalidates the pending action; an old download must not later apply it to a changed story.
- Authoring diagnostics start when the desktop editor is opened. Placement checking may then load the declared hotspot surfaces it needs; ordinary gameplay must not trigger whole-story artwork loading through hidden diagnostics.

## Work surface and dragging

- Choose scene framing automatically from the artwork and the **actual game pane**, with no author override. A background is phone-shaped when its height divided by width is at least **16/9** (portrait 9:16 or taller). It fills a pane narrower than **640 CSS px** when that pane is taller than it is wide. Scale uniformly, center horizontally and align the top; crop the sides or bottom as necessary. Phone portrait uses the full available width, including widths above 390px, without side gaps. Measure the dynamic viewport; browser toolbars already reduce the available height, and safe-area insets protect controls.
- In every other case, fit the **complete image** proportionally into the available pane and center it, using **black** for the surrounding bands. This includes landscape phones, tablets, ordinary wide desktop windows and backgrounds less tall than 9:16. Do not crop or distort fitted artwork. Scale cards, item artwork, labels and goals along with the scene, allowing enlargement beyond 390px on larger screens. Landscape phones may show a small portrait scene; no rotation lock or instructional overlay is required.
- Covers and chapters use the same framing rule, so **Start** leaves a shared image unchanged. Authors specify `(center Xpx, Ypx)` and hitbox `(size Wpx, Hpx)` in pixels of the actual background image, measured from its top-left corner, including fractional values. These are background pixels, not CSS pixels. Coordinates stay registered to the complete image through scaling and screen cropping; no separate authoring canvas is declared. This lets authors copy measurements directly from an image editor. The renderer retains its internal 390-unit-wide scene and proportional height for display and saved movable positions. In phone fill mode, keep text labels and touch targets physically readable and text cards sized for the pane width independently of additional scenery enlargement. Do not hide objects or shrink phone text to disguise an overcrowded scene.
- The catalogue at `index.html` keeps its cream background across the whole browser, with no black borders. Its content stays centered, but its scroll surface spans the window: the scrollbar belongs at the far right on phones, tablets and desktops.
- Arriving at a chapter shows its whole viewport at the end of scrollback. There is no downward scrolling beyond the current chapter, including during dragging or when the phone's available height changes. Earlier chapters remain above it. Resizing keeps the current chapter at the bottom, or preserves the relative reading position when the player has deliberately scrolled into history; opening and closing readings does not change that position.
- The latest, bottommost chapter remains active regardless of which chapter is in view. Ordinary work keeps the view there: moving its items towards an edge does not scroll or change chapters. Dragging the background with a finger scrolls freely through visited chapters in either direction; mouse-wheel and trackpad scrolling remain available.
- Suppress browser text selection, tap highlighting, image/link callouts and selection magnifiers throughout the player, including backgrounds, controls, the encyclopedia index and the mobile chapter picker. Suppress browser double-tap and pinch zoom on these surfaces and in readings, while preserving vertical scrolling and the game's own double-tap actions. Accidental native gestures must not colour the scene, magnify it or interrupt play. Only authored chapter prose (automatic introductions and the reopened goals popup) and wonder prose (creation popup and encyclopedia detail page) support native text selection and copying; illustrations and surrounding controls do not. The desktop authoring editor retains its normal text editing and selection.
- The player never displays focus decorations, regardless of input method. Apply this to the catalogue, game objects, Home/debug controls, readings, encyclopedia and mobile chapter picker: focus alone adds no outline, underline, colour change, name badge, reading cue or partner highlight. The main game requires pointer-driven dragging, so keyboard focus cues do not provide a playable alternative and can appear misleadingly after a mobile tap. Keep ordinary hover, press, drag, partner/drop and goal feedback and permanent link styling. Retain semantic controls and internal focus placement/restoration without adding input-mode tracking. The desktop authoring editor keeps its normal focus indicators, caret and text selection.
- Text-based things are rounded cards; hotspots are fixed square frames. Text slots live inside a named construction, use compact rows, and show named empty-slot hints only when authored. Installed parts are labelled. No result catalogue or click-to-build menu belongs in player mode.
- Hover or press shows compatible existing partners. Keep applicable highlights through a drag, including over rich artwork, and through the accepted double-click interval after release until another target is chosen. Hovering another item or station immediately replaces the previous feedback; the old release timer must not clear the new target. If the pointer remains over the released item, expiry returns it to ordinary hover feedback. Moving into empty space during the release interval retains the released item's feedback until expiry. A second click on the same item must not create an off/on flash between taps. Opening a reader clears ordinary partner feedback. Double-click recognition keeps its own timing independently of hover replacement. A creation drop must look different from an ordinary placement. Do not preview the future result name.
- Partner hints answer **“Will doing a drag between these two things help progress anything?”** Progress includes making something, installing a part, fulfilling a placement goal, or setting up an unfinished recipe or goal by putting an ingredient at its required hotspot. It does not require completing the whole recipe now. For `Dough + Wild starter @ Warm cellar`, Dough and the cellar highlight each other before Wild starter exists; Flour does not highlight the cellar merely because it can eventually become starter.
- Preparatory placement remains useful before a compound has all its fittings, or before a later `next:` placement goal is displayed. Consider unfinished authored recipes and goals, with missing ingredients/fittings allowed when they can still be prepared on a compatible branch. Only highlight existing items and visited locations; do not reveal future results. Exclude permanently unavailable prerequisites, excluded or already-created results, completed goals and placements the item already satisfies. An item already at a hotspot can still highlight it if dropping there performs an available operation.
- Logical play exposes compatible reagents and compound fittings without previewing results. Its two explicit modes choose when that information is shown; detailed play also collapses hotspot preparation into the reaction. See [text adventure and logical playtesting](#text-adventure-and-logical-playtesting) for the interaction and its deliberate placement abstraction.
- A single-item hotspot operation is highlighted when it can execute. Parking its unfinished input there does not satisfy a separate receiving-placement requirement; it needs another recipe or goal to justify a preparatory placement hint.
- Hover and press show a useful drag in either direction; once dragging starts, show only targets useful for that dragged item. Two ingredients that require a hotspot highlight each other only when one can actually be dropped onto the other there. Actual combinations retain their full ingredient, fitting and context checks. Amber drop feedback identifies a creation or useful placement; ordinary repositioning alone does not earn that cue.
- Drop targeting uses the axis-aligned rectangle whose opposite corners are the cursor and the centre of the dragged item's final, board-constrained rectangle. A target qualifies when this cursor-to-centre rectangle intersects its hit area, including boundary contact and rectangles collapsed to a horizontal line, vertical line or point. Use measured tile rectangles, excluding floating names, outlines and shadows; fixed stations use their actual circle or rectangle, so a circular station's bounding-box corners do not count. Among targets supporting an available combination or useful placement, prefer those containing the cursor, then the frontmost target within each group. Incompatible items never mask compatible ones, even when the cursor is on the incompatible item. Apply the same selection during preview and release, with amber feedback identifying the selected useful target. If none qualifies, use ordinary placement, including station membership when applicable. This accepts aiming with either the pointer or the object's centre and gives off-centre pickups some forgiveness without letting a distant edge of the artwork trigger an accidental combination.
- A hotspot accepts a contextual combination through its actual occupants. When the hotspot is selected, drag feedback highlights both it and its uniquely selected receiving item as creation targets. A geometrically targeted compatible item can resolve a station's multiple compatible occupants using the drop-target rules above. Without such a target, an ambiguous station leaves the incoming item in place and highlights the alternatives; never choose an occupant by recipe order. The [specification](story-format-spec.md) owns occupant and chapter-surface rules.
- Dragging a thing moves it; dragging empty space scrolls. Recognize drag travel from both move and release coordinates, retaining the pickup offset even when a quick release arrives before an intermediate move event. Small movements within click tolerance remain clicks. Double-tap (or desktop double-click) opens the item’s encyclopedia detail page, even before the goals-screen encyclopedia unlocks; holding never opens one, because a hold can be the prelude to a drag. Keyboard activation remains available. Cancellation, window focus loss, resize and lost pointer capture while a button is still held must not commit an unfinished move or combination. If capture ends after the button is released but before the release event arrives, preserve the gesture so that release completes the drop. Prevent native image dragging from taking over the gesture.
- Decide cross-chapter dragging at pickup and keep that decision for the whole gesture. An item picked up in the active chapter stays wholly inside it, visibly stopping at its boundaries, and never triggers edge scrolling. This protects the pieces needed to finish. An item picked up in an older chapter may move between visited chapters: holding the pointer within 55px of the viewport's top or bottom for 250ms starts continuous scrolling in that direction, including while the pointer stays still. Leaving the edge or changing direction resets the hold; release and cancellation stop scrolling. Scroll limits remain the first and latest chapters.
- An older item may enter and leave the active chapter during the same drag. Dropping it there makes its next pickup subject to the active-chapter restriction, regardless of where it was first encountered. Accumulating older items there is an accepted tradeoff; **Restart chapter** restores the arrival arrangement and removes that accumulated clutter. Fresh arrivals have no scroll-triggering drags among their own items, while background scrolling still lets the player retrieve older objects.
- Drags should be predictable: when no useful target is selected, dropping A onto incompatible B leaves A where it was released, even when their rectangles overlap. Keep the pickup offset and ordinary board-edge limits; an incompatible item does not send A back to its starting position. A pause before releasing must never be required to commit an ordinary move.
- Keep a stable back-to-front order for movable items. Picking up an item brings it foremost immediately and leaves it there after release; newly created items and new supplies appear foremost. Hover, partner/drop highlights, keyboard focus, reading, redraws and resizing never reorder items. Highlights stay in the highlighted item's layer: if B is partly behind B2, B2 also covers that part of B's combination highlight. Save the order with their placements; chapter restart restores its arrival order. If A covers B, the overlap belongs to A: grab B through an exposed part or move A away. Fixed hotspots remain behind movable items. This makes overlapping drags and subsequent pickups predictable.
- Both text cards and icons use their full measured rectangles for the visible panel's board-edge limits, retaining the pickup offset. A dropped tile's whole rectangle stays within its destination panel; right-edge dragging and release agree, and reloading preserves the placement. Resizing temporarily brings otherwise cropped movable items within reach without overwriting their saved scene coordinates; expanding the viewport restores their arrangement unless the player moves them. Measure text wrapping and compound slot rows as part of the card's height, including at narrow screen widths.
- On a successful combination, anchor the result at the drop destination using the inputs' final computed dispositions; see the [result-placement matrix](#result-placement). Animate the birth without forcing a wait. Never duplicate an existing result, including an incorporated part.
- Earlier panels remain in scrollback. Carry uses actual existing objects and their latest positions. The [chapter arrival layout](#chapter-arrival-layout) reconciles objects brought from different chapters while protecting fixed working places and space for new supplies. Ordinary creation, resize, reading and reload preserve settled positions.

## Chapter arrival layout

- Use the same measured layout for icons and text cards, including wrapped labels and compound rows. An icon's arrival footprint includes its transient name badge above the image, measured even while hidden; tall stacks must not fit their pictures by clipping the first name off the screen. Work within the visible panel, preferring space above the measured goals with breathing room above the goals and below new supplies. Do not shrink artwork or text to disguise crowding.
- Debugger checkpoint jumps have no player arrangement to preserve. Prefer rows centred horizontally, with the whole group around the visible page's vertical midpoint, instead of crowding the top. Start new supplies in their own rows below retained items. Prefer 28px between items at scene scale; reduce that spacing before allowing item overlap. Reconcile the whole arrangement around hotspots and fixed authored starts or inherited occupants. If it cannot fit without overlap, use the ordinary supply reservations and overlap fallbacks below, retaining the centred starting preferences. This applies to checkpoint jumps, including the first chapter; ordinary chapter arrivals preserve the player's arrangement as described below.
- Place newly supplied primitives with authored starting centres exactly at those points. These anchors reserve space before automatic placement and may overlap hotspots. Their authored starts apply only on first arrival; subsequently they are ordinary retained objects.
- When a chapter has no explicit background, it inherits the previous background and hotspots. Items already occupying those inherited hotspots retain their exact positions and hotspot membership. Treat them as fixed obstacles for other items. A chapter with an explicit background does not receive this exception.
- Plan a concrete arrangement for all remaining new supplies near the bottom before placing retained objects. Reserve its region and a gap above it. Try alternative row arrangements and higher reservations when stations obstruct the bottom. If a separate lower group cannot fit, pack the supplies into other clear pockets as a group.
- Place retained objects by their last occupied chapter, starting with the previous visited chapter and working backwards. Use their latest coordinates, not their original creation positions. Within each group prefer the least displacement; among equally distant placements prefer one closer to the visible panel centre. Deterministic alternative arrangements help avoid an early small object blocking the only space for a large one. If separate chapter groups cannot fit within the ordinary overlap allowance, reconsider all carried objects together, keeping authored anchors and new-supply reservations fixed. If the reservations themselves prevent a usable arrangement, repack all movable arrivals together, allowing the supply grouping to yield while preserving authored anchors and inherited occupants.
- Normally allow at most 10% of any item's measured rectangle to intersect the union of other item rectangles. Check the existing objects' budgets as well as the arriving object's: several small overlaps must not conceal much of a small object. Fixed authored arrangements can already exceed the current allowance; automatic placement must not worsen excess beyond that allowance. Retry the whole movable arrangement as space constraints yield, before gradually increasing item overlap. Even when greater overlap is unavoidable, compare complete arrangements to reduce concealment; never fall back to placing each item independently at the same corner.
- If any new primitives arrive, prefer to keep retained objects from before the previous visited chapter entirely within the visible panel's upper two-thirds, subject also to the supply reservation. Keep valid old positions where possible; relocate rectangles extending below that boundary into available upper space. If the group cannot fit there within the ordinary overlap allowance, try the remaining unreserved working area. Without new primitives, omit the two-thirds preference and supply reservation, but still reconcile collisions.
- Relax spatial preferences in this order: reduce the gap above goals down to zero; allow items into the goals' area; allow overlap with hotspots; only then increase item overlap beyond the normal allowance. Relax edge comfort insets when needed to use the visible panel. Keep icons usable on short phones even when browser toolbars leave too little height for all preferred clearances. When goals must be covered, minimize that coverage. When hotspots must be covered, prefer their edges and minimize covered receiving area before goal coverage or displacement, leaving drop areas exposed where possible. Circular hotspots use their circular interactive area; other hotspots use rectangles. Authored starting positions and inherited occupants retain their exceptions. Automatic visual overlap never changes hotspot membership, triggers a recipe or satisfies a placement goal; those remain player actions.
- After placing retained objects, lift the planned new supplies to a short distance below them when possible, checking the new positions against hotspots and items again. Preserve the existing grouping and gap, but hide the dotted divider and its **new items** label for now. Retain the divider's code and placement calculations so its display can be restored independently of item layout. Save the final positions and capture them for chapter restart; ordinary redraw, reload and reading do not re-run arrival layout.


## Goals and readings

- Center terse goals at the bottom of the screen, without an “Objectives” heading. Reserve space for a checkbox beside each goal so completion does not shift its text. Use a light translucent backing rather than opaque badges, keeping the text and checkboxes readable over artwork. Clicking unobstructed goals reopens the chapter text.
- Keep goals above the scene background and below every hotspot and movable item, including while an item is picked up, dragged, released or cancelled. Preserve that layer order through scrolling and redraws. During ordinary play, goals remain fully painted behind objects, visible through transparent artwork and immediately revealed as objects move away; never cut rectangular holes around items or dim the goals merely because an item is dragged. Hotspots and items take pointer precedence where they cover a goal. This keeps overlapping objects visually continuous, without goals popping over a drag or leaving stale gaps behind it.
- Show the current stage of each sequential goal chain, replacing an achieved intermediate with its next task and retaining a checked final stage. Keep the wording of a partly satisfied multi-condition goal intact. Gold on an item identifies a current witness of a displayed completed goal in the active chapter, not permanent achievement status; moving a placement witness away removes that visual status without undoing the recorded achievement. The [specification](story-format-spec.md) owns goal latching, chain requirements and simultaneous-goal limits. Staged goals keep attention on the next useful work without prohibiting early discovery.
- When a displayed goal becomes checked or changes to its next stage, pulse that row immediately. Use one quick expansion to 120% (limited as needed to keep long goals within the pane), then a gradual return over an 800 ms cycle, with a borderless bright amber backing and warm glow. Preserve other rows' positions and the goals' layer, and reserve room inside the scroll clip. The stronger treatment makes the reminder visible during active play; reduced motion uses the same colour emphasis without scaling.
- On the sixth movable-item pickup since the last pulse, start a reminder immediately on pointer down, while the item is still held. Each accepted pickup counts once, regardless of its later movement, combination or cancellation; release does not count again. Fixed-hotspot presses, reading controls and popup dismissals do not count. Choose the displayed unfinished goal with the fewest remaining productive actions from the current game state, counting combinations, fittings and necessary placements, with the visually higher row winning ties. Rank only the current stage of a sequential chain. Prepare the [bounded logical ranking](engineering.md#state-and-continuation-analysis) ahead of the trigger; if the current state's result is unavailable, use its visually highest unfinished goal immediately. Do not wait for analysis, expose the solution or reorder the goals.
- Pulses run concurrently with dragging, combinations, creation feedback, artwork loading and readings; there is no idle-time requirement. Never pulse while a tutorial is active: opening drag, paired hotspot drag or click-on-goals. Also suppress them in the mobile debug picker and while the page is hidden. A displayed creation wonder cancels an active periodic reminder and suppresses further reminders for that pickup and the next, allowing them from the second subsequent pickup. Dismissing or redrawing the wonder does not advance the delay; another wonder starts it again. Goal-change pulses have higher priority than wonders: show them immediately even with the wonder popup open or its reminder cooldown active.
- Treat pulses as disposable attention feedback. A newer goal change immediately cancels the current pulse and replaces any queued change with the newly changed rows. Chapter completion replaces older attention feedback with the final changed-goal pulse; entering the next chapter cancels any remaining outgoing animation. A tutorial appearing stops any active pulse. Ordinary dragging and board redraws preserve the current animation, and its finish must not redraw or reposition a held item. Every pulse restarts the pickup counter. Entering a chapter or deliberately opening goals starts a fresh count; opening goals also acknowledges queued or active pulses. Chapter/story restart, checkpoint jumps, reload and live story replacement start fresh attention tracking without replaying previous goal changes. Attention counters are session-only presentation state and do not alter saved gameplay or tutorial accomplishments.
- When all goals are complete, pulse the newly completed goal once while the checked goals remain anchored at their normal screen position and fade into nothing over the pulse cycle. Start the chapter arrow's fade-in at the same time underneath the goals, without lifting or displacing them; during the overlap, paint the goals above the incoming arrow and both below game objects; keep it enabled from the start and make the departing goals pointer-transparent. Do not wait for either animation before allowing navigation. If a creation wonder is open, run this visual transition behind it; the reading still blocks interaction until dismissed. The final goal change retains priority over wonder suppression, while tutorials still suppress pulses. Its entrance should make the change visible, distinct from the arrow's ongoing attention animation. Do not replay either effect on ordinary redraws or when reloading an already-ready chapter. A new background uses a down arrow; an inherited background uses a right arrow. Advance only through that arrow. Reduced-motion users get the completion state change without movement or a forced wait.
- Items with applicable nonempty encyclopedia text show a small muted open book (half the goals glyph’s dimensions) centered over their top edge while pressed or dragged, including the existing 400 ms release-feedback window. On devices with hover, also show it while the item is hovered so desktop players can discover readings without picking up an item. For icon artwork, place the book just inside that edge to leave room for the name above. Compatible partners do not show this book. It enters once briefly, then stays still; reduced motion skips its entrance. The cue is available before the encyclopedia unlocks.
- Wonder and encyclopedia-entry readings have no book decoration; the glyph belongs only on the item’s reading badge and the chapter’s Encyclopedia control.
- Reading and wonder popups render only their authored Markdown paragraphs and images. Background declarations are scenery metadata, excluded from readings; ordinary images always remain reading content, even at the beginning of a chapter inheriting its scenery. This lets authors illustrate an introduction without changing the setting or its hotspots. Do not append an item-name caption, title or attribution; an italic name appears only when explicitly authored. Chapter prose likewise gets no generated chapter heading or duplicated goal checklist. Preserve authored paragraph order and emphasis, including on later renamed items. The [authoring guide](story-authoring.md#write-wonders-and-attribution) governs standalone explanations, desk voice and authored italic conclusions; these are content, not generated captions. Use readable serif prose and fit illustrations within the reading area without cropping their content. Primitive reading is deliberate. Nonempty creation popups appear once per applicable configuration/run, and their acknowledgments survive saving.
- Creation feedback and deliberate reading use the independent texts defined by the [wonder syntax](story-format-spec.md#specification). The popup should respect the player’s current work; the encyclopedia can offer more explanation and citations. Show only the popup half automatically and only the encyclopedia half when double-tapping or keyboard-opening an item. An empty popup creates no notice or Continue step. An empty encyclopedia half creates no entry or book indicator, and manual reading does nothing; popup-only text cannot be reread after dismissal. The encyclopedia does not prepend the popup. Without a divider, both use the same text. Existing slot conditions apply to both destinations.
- Keep readings within the game area, scroll long content, and leave the desktop editor usable alongside them. New readings open at their beginning; initial keyboard focus must not scroll past their opening text or illustration. Dismissal and returning from a reading preserve the board's arrangement and scroll position. Manual reading does not create another discovery or acknowledge an unrelated pending wonder. Creation wonders have a clear **Continue** action and never require waiting for an animation. Avoid gameplay toasts for ordinary movement; visible failures belong to [persistence and recovery](#persistence-and-draft-recovery).

## Text adventure and logical playtesting

The human command-line game and AI playtester share an adventure runner over the existing game engine. Starting either requires exactly one of `--fast` or `--detailed`; an AI session retains that choice for subsequent views, replies and verification. The [evaluation guide](fun-and-evaluation.md#logical-playtesting) owns commands, experiment selection and report requirements; its [rubrics](fun-and-evaluation.md#player-and-grader-rubrics) own AI recording and grading. Both players receive game-authored text and actual game events. New AI sessions also require explicit `--guidance TEXT`, allowing `--guidance ""`, to make the organizer consider audience and purpose. That context is frozen and shared unchanged with graders.

### Shared presentation

- A start prints the story title and subtitle/description. For every completed chapter, show its title and intro, the normal **Goals / Hotspots / Items** arrival board, and actual checkpoint actions as `Step N combination: A + B @ H -> C` or `Step N preparation: ...`, with wonders and goal changes in order. Number this background history separately within each chapter; it is not decisions made by the current player. Skipped chapters have no played arrival board: mark Items as skipped, omit Hotspots and preserve actual skip-bridge prose once. Do not invent a recap or reveal unperformed recipes. The checkpoint selector is one-based; past and active headings use `## Chapter N. Title`.
- The active chapter shows its intro, then **Goals**, **Hotspots**, **Items**. Omit Hotspots when empty, including refreshes and historical boards. Only the current chapter's items and active hotspots are selectable, including inherited hotspots. Earlier boards are history. List current names, installed components and named empty slots, without descriptions or chapter annotations. Compounds display as `Foo[]` or `Foo[Bar1,Bar2]`; hidden slot requirements remain hidden. Fast mode also displays current hotspot membership; detailed mode has no persistent membership.
- Never show primitive descriptions or wonder text in board listings. After an action, show its result, then each nonempty popup half indented directly beneath its result, without repeating item headings or internal line breaks, then goal changes. Acknowledge readings internally. Completed checkpoint history also uses only the popup half; encyclopedia text never becomes automatic text-play output. Later turns show changes instead of repeating the board.
- Human play prints **All goals completed** and continues automatically to the next chapter and eventually the ending, preserving engine skipping. AI chapter assignments stop at their boundary and request the final reflection and report. Decision numbers restart at 1 on chapter entry.
- A human presses Enter to refresh the board without a decision; this is repeatable, including on the first move. AI look is available once per decision after the first gameplay decision in a chapter, and returns after the next decision. It preserves the current step and any pending reflection. Record the subsequent actual reply with a harness-owned `lookedAgain` boolean and retain the refresh as supporting metadata; a look alone adds no action entry. Interruption after looking stays pending.
- Validate complete AI replies before mutation. Reject stale steps, malformed commands and missing recording fields without counting a decision. Raw engine state, action IDs and unperformed developer routes remain internal. Neither interface has a quit command; terminal interruption/end-of-input ends human play.

### Fast play

- Show numbered compatible combinations, compound fittings and useful hotspot preparations with future results hidden. Include clearing an occupied hotspot when it restores another compatible action. Offer one direction per recipe, preferring manuscript order when legal. Receiving-location differences do not create duplicate reversed choices. Show `@ Hotspot` only for recipes that require it, in both menus and history.
- Print `Created: Item.`, fitting or placement changes, omitting input-retirement notices and the creation's hotspot. Follow the result with **What combination will you make for step number N?** and consecutive numbered options.
- Humans enter a number. Any nonnumeric input, including Enter, refreshes the board; an unoffered numeric choice is an error. Do not print a look option for humans.
- AI replies choose a number. When available, append `L. [Look again at what's available]`; a look reply contains only `{"step": N, "choice": "L"}`.

### Detailed play

The player decides whether to inspect for compatibility or act on an inference. This makes seeking information an observable decision instead of giving the entire compatible-action menu before every choice. Only `inspect A` and `combine A with B` are gameplay commands; do not display numbered combinations. The human prompt is **What will you [I]nspect or [C]ombine for step number N?**, making the shortcuts visible without a separate command-help sentence. AI retains **What will you inspect or combine for step number N?**

- Inspecting an item lists **Can combine with:** and unique bullet-listed partners: another item for a non-hotspot recipe or compound fitting, and a hotspot for an available single-item or contextual hotspot reaction. Inspecting a hotspot lists all available item operands of its reactions. Include currently completable placement goals. No output names or unavailable ingredients are disclosed. With no partners, show `- (none)`.
- If exactly one executable operation involves the inspected object, first show its normal inspection partner list, then `Combined: with B.`, naming the automatically selected partner, then the normal combination report. This explains the implicit action to both humans and AI. For an inspected item used at a hotspot, name the hotspot as the selected partner; for an inspected hotspot, name the selected item. Retain the additional third-ingredient message for contextual reactions. Count that inspection and its automatic result as one decision. Count distinct operations, not distinct partner labels: several reactions at one hotspot do not make inspection automatically choose one.
- Combining two items performs their available non-hotspot recipe or fitting. An item–hotspot command works in either order. Prefer an available single-item operation, then the first available contextual reaction in manuscript order, then a placement-only goal. Contextual reactions automatically use an available third ingredient with the required fittings, irrespective of its placement. Print `Combined this together with: B.` before the result. The player never specifies three operands or chooses a receiving placement.
- Hotspot setup and cleanup are internal engine actions in the same decision. Clear all available items' hotspot membership after the operation and on detailed chapter arrival, including checkpoint starts. The intention is to omit obvious preparatory drags from the text interaction. This is an explicit abstraction of browser play; browser drop priority, occupant ambiguity and geometry remain governed by the work-surface rules.
- Placement-only goals remain completable with the same item–hotspot command: print `Placed: A at H.` and retain the achieved goal after cleanup. When a single goal requires several simultaneous placements, perform its available required placements together and report them. Do not offer preparatory placements for reactions whose ingredients or fittings are still missing.
- Report `Created: C.` or `Transformed into: C.`, using the engine's actual input dispositions. Prefix `Consumed: B.` when applicable; name all consumed inputs. Transformation need not identify which input changed. Fitting reports `Slotted in: B[X,A].` Preserve result wonders, empty-slot information and goal changes.
- A well-formed `combine A with B` first performs the requested combination if available. Otherwise, if A has no executable operations, report **That cannot be combined with anything**. If A has any, report **That can't be combined like that, but here's how it can:**, then perform the exact same inspection behavior for A: show its partner list and automatically execute an operation only when exactly one involves A. This models the compatibility feedback received while picking up A and the obvious adjustment it can prompt. Keep A as the first operand; do not search for alternatives involving B. Preserve the requested command in the record, name the automatically selected partner and report the actual result. Count the attempt and any automatic operation as one decision, without chaining further operations from its result. Every inspection also counts, including an empty or repeated inspection. Unknown or ambiguous names and malformed commands are errors, change nothing and do not count.
- Resolve case-insensitive exact names or unique full-word prefixes across **all** active items and hotspots, independent of compatibility. Exact names take precedence over longer names with the same prefix. A compound accepts its full displayed label or its base name. A partial word such as `War` is not an AI name for `Warm hammock`; `Warm` works when unique. Quoted names are supported in terminal commands. AI uses structured commands, without additional quotes inside the name strings.
- In an interactive terminal, `i` expands to `inspect ` and `c` to `combine `. Typed letters autocomplete as soon as one current name matches, adding quotes and, after the first combine operand, ` with `. Completion considers every current item and hotspot, even incompatible ones. Keep normal line editing and require Enter to submit the completed command. Piped input accepts the same full commands and `i`/`c` aliases; blank lines look. Other invalid text is an error.
- AI uses `"choice": {"inspect":"A"}` or `"choice": {"combine":"A","with":"B"}` inside its full structured decision reply. A look contains only `{"step":N,"choice":{"look":true}}`; the same first-move and once-per-decision restrictions apply. An unsuccessful combination or inspection still produces a result for the following reflection.

Retained evaluations identify the playstyle and tested manuscript's chapter titles. Do not combine modes into one chapter score or compare their decision-density ratios as the same condition. The [report format](fun-and-evaluation.md#run-files) owns headings and assembly rules.

## Result placement

For a two-item combination, A is the dragged item and B is the receiving item, regardless of their order in the Markdown recipe. Use their **final computed dispositions**, after the engine protects ingredients still needed later. A preserved A returns to its exact source position and placement; a preserved B stays put.

| Dragged A | Receiving B | What remains | Where C appears |
|---|---|---|---|
| preserve | preserve | A returns; B stays | At B's corner with a small overlap |
| preserve | transform | A returns; B disappears | Replaces B in place |
| preserve | consume | A returns; B disappears | Occupies B's vacated position |
| transform | preserve | A disappears; B stays | At B's corner with a small overlap |
| transform | transform | Both disappear | Replaces B in place |
| transform | consume | Both disappear | Occupies B's vacated position |
| consume | preserve | A disappears; B stays | At B's corner with a small overlap |
| consume | transform | Both disappear | Replaces B in place |
| consume | consume | Both disappear | Occupies B's vacated position |

Centre a replacement on B's former centre, using the actual dimensions of both tiles and adjusting only enough to keep C on the board.

When B survives, try C at its four diagonal corners. Overlap by 10% of the smaller width horizontally and 10% of the smaller height vertically; use the containing rectangles even for circular objects. This small shared corner keeps the creation visibly connected to its parent while leaving both accessible. Choose a position entirely within the visible board and clear of other available items, preferring the result centre closest to the usable board centre. If no diagonal qualifies, try the four side-centred positions with the same 10% overlap along the joining axis and the same inward preference. If all eight positions are blocked, fit them within the board and choose the least total intersected area with other items, including B; break ties towards the centre. Keep the player's existing placements intact. Reserve top-edge room for the new icon's name without including floating names in the overlap rectangles. This applies equally to text cards and icons, including drops between visited chapter panels. Logical chapter and hotspot placement follow the [specification](story-format-spec.md).

Compound installation adds the component to the existing compound, which stays in place even when it was the dragged item. Single-item hotspot operations create their result at the receiving hotspot's chapter and location.

An applicable hotspot `place:` instruction takes precedence over the default matrix when an item enters that hotspot on a chapter panel and for newly created results there. Try its exact centre using measured item dimensions after input retirement; occupied or off-board rectangles fall back to the matrix/ordinary drop. Other existing items stay put. An item already occupying that hotspot on the same panel keeps its released position when rearranged, so the player can adjust the initial arrangement. Leaving the hit area and returning during one drag still counts as rearranging; dropping outside and then re-entering can snap again, including after goal completion. Single-item hotspot results without a usable authored destination are centred using their actual dimensions. Redraws, resizing and reload do not reapply the instruction. Syntax and containment checks belong to the [specification](story-format-spec.md).

- Display scenery exactly as authored. The game must never apply a translucent wash, tint, scrim, opacity adjustment or colour grading to background images. The fade is part of the background files, following the authored-scenery rule above.

- The [icon reference collections](../references/icon-sets/) are author references, not a player-facing style selector.

Give such resource icons compact, readable drawings so they leave room for the scene and the work. In this mode, moving a token does not imply physically carrying the represented installation. Backgrounds establish the world. A fixed facility may use a clearly identifiable hotspot token, or a registered receiving area over the actual painted feature under the transparent-hotspot rule below. Decorative scenery alone does not become interactive. This supports stories whose combinations express work across different physical scales. Keep the convention consistent within the story, preserve causal and identity continuity, and record its chosen visual language in the active design brief.
- An item's chapter-dependent name and icon follow the current progression chapter everywhere, including earlier boards and the encyclopedia. Human and AI text play use the current displayed name, with each replay step using its own chapter's name.
- Icon size and fixedness are independent. A story may use larger movable circles to distinguish pivotal creations while preserving the ordinary drag gesture. Reserve fixed treatment for an actual receiving context; importance alone does not make a hotspot.
- An authored icon replaces the text card, preserving the image's transparent outline and its own backdrop. At the 390 × 844 reference viewport, display it at one quarter of its intrinsic pixel dimensions; other viewports use the scene's uniform scale described in [work surface and dragging](#work-surface-and-dragging). Unusually wide artwork fits within the panel while retaining its aspect ratio. Keep a usable touch area for small images. The [specification](story-format-spec.md) owns icon syntax and consistency checks.
- A hotspot may also use transparent artwork at quarter size, centred on its authored image-relative point. It stays fixed and receives the same contextual combinations and placements as a text hotspot. Both icon and text hotspots use a plain black dotted outline on hover, press or compatible-item highlighting, with no white edging or shadows, to distinguish fixed locations from draggable items. Show the icon hotspot's name above its artwork; use amber feedback for an accepted drop. Preserve its connected image when the board updates, and fall back to its readable name if loading fails.
- A hotspot can change its chapter-local artwork after another item has been created, using the [conditional icon syntax](story-format-spec.md#specification). This lets authors show a changed world while preserving the ordinary single-result combination model. The last satisfied directive in source order wins, with a preceding local default or the item's current icon as fallback. The condition remembers creation even after its trigger is consumed or installed; restored progress and live edits determine the selected image. Inherited scenes retain the directives, while another scene's explicit hotspot declaration has its own presentation. Keep the hotspot's identity, centre, stacking order, fittings and connected DOM nodes; changing its artwork does not announce a new item or open a reading. Prepare and decode changed artwork before displaying the accepted action, including affected scrollback hotspots. Its measured dimensions and circular marker govern the ordinary hit area; an authored rectangular hitbox remains independent of noncircular artwork. Placement diagnostics check all declared variants without gameplay-state enumeration.
- A fully transparent hotspot icon can define the interactive area of a feature painted into the background. It retains the same name, feedback and minimum touch area as other hotspots.
- An authored rectangular `hitbox:` separates the receiving area from the full registered artwork. Use it when a cable, shadow or other connected detail must remain visible outside the equipment that receives the next action. Hover, clicks, dragging, dotted/accepted outlines, names, placement checks and arrival clearance all use that rectangle, including the ordinary minimum touch area. Artwork outside it remains visible and does not intercept pointer input. The image and fitted layers retain their original scene centre and scale; narrowing a receiver must not resize or move the painting. The [specification](story-format-spec.md) owns syntax and validation.
- Within each chapter, paint hotspots back to front in their Markdown Hotspots declaration order: later declarations cover earlier ones. Inherited scenes retain that order, and a newly constructed fixed item takes its declared place rather than appearing on top because it was created later. Artwork, name badges, highlights, pointer hits and drop priority follow the same order. Hovering or focusing a hotspot does not raise it. Movable items remain above the fixed layer.
- Show the item's current name when hovering, pressing or dragging it, and show the names of compatible partners at the same time. Item and hotspot name badges normally sit immediately above the image, clear of a finger dragging it: white sans-serif lettering, a faint light border, rounded corners and a translucent black backing. For manual positions, dragging and exact authored anchors at the top edge, keep the image fixed and pin the badge to the scene's top; its text may overlap the image there. These edge exceptions keep names readable without moving physical targets or changing the drag pickup point. Apply them while dragging as well as at rest. Use the same feedback lifetime as text cards, including the double-tap interval. Keep the accessible button name available while the visual badge is hidden.
- A newly created icon shows its name automatically for 1.5 seconds, then fades it out over 200 ms. Redrawing or resizing the board preserves this lifetime; reloads, chapter jumps and resets do not replay creation feedback. Hover, press, drag and partner feedback keep the name readable independently of that fade.
- A selected or compatible icon has a dotted outline within its full image rectangle. An authored `(circular)` icon instead gets a circular outline within those dimensions. Accepted creation targets have a distinct amber outline and glow. Preserve transparent artwork rather than filling the whole image rectangle with highlight color.

Its rectangular corners do not activate it. Use the same shape for arrival clearance and authored destination validation. Other hotspots retain rectangular hit areas; transparent pixels remain interactive within the applicable shape.
- Fixed artwork keeps its authored quarter-size dimensions, including scene-wide replacement images. The ordinary scene scaling and viewport crop apply to both together.

- Measure icons and the actual wrapped height of their transient badges before [chapter arrival layout](#chapter-arrival-layout). Missing or failed artwork falls back to a readable text card, including fitted parts.
- Primitive icons with authored starting centres use those points on their first arrival. Arrange automatic arrivals around them; carrying or reloading an existing item preserves its normal placement behaviour. See the [specification](story-format-spec.md) for syntax and restrictions.

Show every currently applicable nonempty encyclopedia half for the selected item, preserving the authored content rules in [goals and readings](#goals-and-readings).

## Contextual tutorials

- Each manuscript supplies exactly one `(tutorial)` recipe in its first chapter, immediately executable with its opening inputs and no preparation. This ensures the demonstration offers a valid first move. The [specification](story-format-spec.md) owns marker syntax, directed operand selection and lint errors for count, chapter and readiness violations.
- After Start and the first chapter introduction have closed, demonstrate that recipe's directed drag unless this story's drag tutorial is already complete: for `A + B -> C`, drag A onto B; an item/hotspot recipe targets the hotspot. A thin curved arrow connects the live source and target, a translucent copy of the source demonstrates pickup/travel/release, and the target gets a restrained outline. The real objects remain still and usable; the demonstration never creates or previews the result. Use the object itself to demonstrate the action without obscuring play with a large animated hand or instructional text.
- Show only the highest-priority tutorial that can currently be demonstrated: opening drag first, two-item hotspot combination second, goals third. An unfinished but unavailable lesson does not suppress another lesson. Goals do not require a previous combination. Keep the existing opening `(tutorial)` marker; the hotspot lesson needs no annotation.
- Discover the hotspot lesson dynamically from a two-item recipe `A + B @ H -> C` when both available ingredients and H are together on the current chapter panel. Required compound fittings must be present and the result must still be creatable. Check that the demonstrated placement and combination work through normal drop resolution, including competing operations and occupants; do not wait for an ingredient to have been placed at H already. ## Story analysis comparisons

Comparison-table column titles come from the input paths so arbitrary manuscripts receive compact, recognizable names without story-specific aliases. Use the basename without `.md` when it is unique among the selected inputs. For repeated basenames, prepend only enough parent directories to distinguish each path. Within each repeated-basename group, remove any shared prefix of the leading directory names through a hyphen, underscore, dot or whitespace boundary, provided every directory name stays nonempty. Thus `mars-v8/mars.md` and `mars-v9/mars.md` become `v8/mars` and `v9/mars`; a separately selected `cookbook.md` stays `cookbook`. Keep input order. The [authoring guide](story-authoring.md#analyze-combination-structure) describes commands and counting conventions.

The analyzer requires explicit file operands in every output mode. Resolve them against the current directory, preserving input order and deduplicating resolved paths. Shell globs select groups of files; there is no implicit catalogue selection, story-name lookup or `--include` option. Accept any filename or extension. Because the parser deliberately recovers from malformed input, recognize a story only when it has at least one parsed chapter, at least one combination and at least one goal. All three are required: prose with chapter-like headings, goals without combinations and combinations without goals do not qualify. Existing parse diagnostics and analysis failures still apply. Filename conventions do not affect this decision.

Table mode processes each input independently. Print a warning naming each unreadable, unrecognized or unanalyzable input and its reason to stderr, keeping stdout and saved tables free of warnings. This lets shell globs include companion documents without blocking a comparison. Compute column titles from the surviving stories. Succeed when at least one story remains; if none remain, fail without printing a table or changing an existing output file. Never overwrite any supplied input, including skipped files. Plain-text and JSON modes fail on an input error.

- Preserve concurrent work from other tabs under **Saved copies**, without replacing the open buffer. Show a notice when another tab saves different text.
