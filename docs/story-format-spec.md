# Story format specification

This document defines the Markdown language, game semantics and required diagnostics. Use the [authoring guide](story-authoring.md) for story design and the [README](../README.md) for repository layout and tools.

## Specification

1. Each file is a story. The filename of the story is ignored. The story has a heading and text, which will appear in the main menu of the game. The markdown may include `> NOTE:` quoted blocks, including at any indent level inside lists. These are comments for the story-author and have no effect on the game logic for the story.
2. Each story is made up of a series of chapters, starting with `##`. The chapter has a name, but this name never appears in the game. (except maybe in debugging tools). There is an optional final chapter, by convention named "The End", with no goals or hotspots or items. It's only role is to convey its chapter-describing popup as the final text of the story.
3. A chapter has an optional image, optional markdown paragraphs, and then sections "Goals", "Hotspots", "Items", "Combinations" each in bold with bullets under them. These sections may be omitted.
   - Image paths are relative to the story Markdown file.
   - The background cannot change within a chapter; a different background requires a new chapter.
   - Every chapter is shown to the user with an image. If the image is provided in markdown then the chapter's image is that and it carries over no hotspots; if no image is provided in markdown then the chapter's image is the same as that of the previous chapter, and it carries over the hotspots from the previous chapter. Note that the user might see two copies of the same image when they scroll back through their game's history.
   - How to distinguish the optional image? It will be the very first content of the chapter, and it will be in a paragraph with no other text after it. Thus for instance `## Chapter1\n![img1]()\n\n![img2]()\n` means that img1 is the background, and img2 is an image to display inside the chapter popup. It's not possible to have a chapter popup start with a "paragraph image" unless it has a background image.
   - If the optional text is present, then starting this chapter causes a popup text to appear. This text may include Markdown images, e.g. avatars of the philosophers.
   - There may be a paragraph of markdown which starts "[If skipped]". If the chapters goals were completed before it even started, then we skip the chapter, and accumulate these "if skipped" paragraphs into text of the next uncompleted chapter we land on (or dropped entirely if there isn't one).
   - Note that there's no such thing as "return to an earlier chapter". The chapters in a book are strictly monotonically increasing. It's possible for a later chapter to have the same image/hotspots as an earlier chapter, though.
4. Much of the markdown can refer to other things, especially goals, hotspots and items.
   - Only certain places in the grammar allow references, e.g. after "with" for items. Note that there are no places where we have prose that contains reference.
   - A reference can be enclosed in quotes, bold or italics to help it stand out, or it can also be just free text in places where the grammar is unambiguous about its start and end.
   - There are various declaration sites for things. These are written with the same grammatical rules as references.
   - At a declaration site, you can also write an identifier first in backticks, e.g. `foo` bar. You must refer to this by its identifier `foo`.
   - There is a single global namespace in the story for backtick identifiers, and a separate global namespace for non-backtick identifiers. If there are any clashes, then we take all references as referring to the first, and we lint against it.
   - For compound items, "A[B,C]" refers to an item A with at least slots filled with B and C. "A" is short for "A[]".
5. Goals has a bullet list of goals
   - Each goal has the form "Goal text" or "next: Goal text". The ones marked "next" will only be displayed when their immediate predecessor has been completed, and it's a lint error for the first goal to be "next".
   - A goal with exactly one condition may be written "Goal text -- Condition", including "next: Goal text -- Condition". This is shorthand for the same goal with Condition as its single sub-bullet. Any permitted form of goal condition may be used, including item, item @ hotspot, compound references and composition rules. An inline condition cannot be combined with sub-bullet goal conditions.
   - Each goal has one or more conditions (bullets). The conditions may have the form "item" or "item @ hotspot". If there more than one condition then they're taken by default as disjuncts. You are allowed to write explicitly "or:" in front of all items to show they're disjuncts, or "either:" for the first and "or:" for all the rest. Likewise you can write explicitly "and:" or "both:/and:". It's a lint error to combine disjuncts and conjuncts.
   - Conditions may also be writen "A + B -> C". This both declares a combination rule with the normal syntax, and also counts as an item goal "C". (Note: if there were another rule E+F->C in the story, then the goal could be satisfied by that construction too; if C already exists, then that will satisfy the goal). Composition conditions are not allowed to have sub-bullets under them (for follow-on compositions).
   - The goal "- A[B,C] @ H" means item A must have items B and C inside its slots, and be placed at hotspot H.
   - If there are multiple goals, they are by default conjuncts of goals. You can use the same "either/or/both/and" labelling in them. Within a `next:` chain, every goal remains required: a chain is complete only when all its goals have been achieved. The chapter's conjunct/disjunct combines these complete chains. `next:` controls sequential display, not which goals are required, and does not prohibit making a later result early; an already achieved later goal never bypasses an unfinished predecessor.
   - Once a goal is satisfied, it remains satisfied even if its witness later moves or transforms. For example, moving an item away from a required hotspot does not revoke the achieved goal.
   - Goal text is fixed: a goal such as "Cook X and Y" does not change to "Cook X" or "Cook Y" when one condition is satisfied.
   - Warn when a chapter starts with more than two goal chains, counting goals that are not marked `next:`. Report the count for author review, and suggest `next:` when sequential disclosure makes the goals easier to follow. Every goal in the chain remains required; the warning is not a requirement to serialize independent objectives.
   - Warn when a goal references an item listed as a top-level Item in a later chapter, unless that item already has a top-level listing or a producing composition rule in the current or an earlier chapter. Check every goal alternative, including those behind `next:`. Identify the goal, item and later chapter in the diagnostic, and explain that this reference may pull later supplies into the current chapter through global recipes. For example, an early contact goal accepting Long range radio should warn when that item and its producing rule first appear at the later cargo sled; Dirty water made at the habitat entrance should not warn merely because it is listed again in the cabin. This is an author-review warning, not an error or a restriction on global recipes. It is deliberately a heuristic: items written only incidentally in compact forms, with no later top-level listing, need not be caught.
6. Hotspots is a list of named hotspots
   - Hotspots may specify normalized image-relative coordinates: `- Signal mast (at 70%, 80%)`. Coordinates identify the hotspot centre, from the top-left of the chapter image, and must lie between 0% and 100%. Without coordinates, the UI uses its stable lower-panel layout.
   - It's a lint error to have hotspots without an explicit chapter image.
   - A hotspot can provide context for a two-item combination, act as the other operand for a one-item combination, or receive an item to satisfy a goal. It never accumulates ingredients or the capabilities of prior occupants. Ordinary placement is freely reversible.
7. Items is a list of items
   - An item can have a wonder-description, one or more markdown paragraphs with optional pictures. These wonder descriptions will be popped up when the item gets created, and when the item is double-tapped or long-pressed.
   - You can do nested items to show how the result of one combination can in turn combine, as a shorthand, so as not to have to write every declaration out at top level. But you still can write them out at top level if you want.
   - Items aren't "declared" explicitly. The set of items in the story and their combinations is the global set of all items/combinations that are mentioned in any chapter. If you write more about an item in different places (in hotspots, goals, items, in different chapters), it all "unions" into the facts about that item and its combinations.
   - An item can be marked as exclusive with another, "- A (exclusive with B)". It's a lint error if these markings aren't mutual (i.e. declared under both items), or if an item is marked as exclusive with more than one other item. It's a lint error if any goals or top-level items can't be satisfied due to exclusivity: this involves, for each conjunction of goals and for all top-level items in a chapter, working back through all ancestors.
   - Creating an item permanently rules out its mutually exclusive partner. Transforming or consuming the chosen item does not reopen the alternative.
   - An item can be marked compound, "- A (compound)". If so it has one or more slot declarations as sub-bullets, either "slot: Name, accepts Reference" or "unnamed slot: accepts Reference". The named slots will appear in the UI with ghost text. This notation only allows a single item to fill a slot. It's implicit that if A has a slot that accepts C, then "A[B] + C [consume] -> A[B,C]". It's a lint error if two slots accept the same item. Incidentally, both named and unnamed slots can be used in goals.
   - A compound item can have a wonder markdown, meaning it will be shown when the basic item exists. Or the wonder markdown might start with "[B,C]" indicating that the wonder text will appear the first time slots have been filled. In this case, double-tapping only shows the wonder text after those slots have been filled.
   - An item declaration can be written "A (or from chapter X, B)" to indicate that once the player reaches chapter X from then on the item will be named B instead. This applies everywhere, including when scrolling back to earlier chapters. For example, adding "Augustine:" helps the player distinguish an earlier claim after encountering other thinkers; returning to the old chapter does not restore the shorter name. Note there's no equivalent facility for wonder-popups on items; that would break continuity. The change in label is to help the user orient themselves, but the expansion into a popup should feel more solid like a permanent record.
8. Combinations. These are lists of combinations, similar to items. They allow nesting just like with items.
   - Although we say that some reagents are "consumed" or "transformed", they really aren't. Every item in the game is really an infinite resource. The words "consume" and "transform" are merely hints to the engine about when to hide away these infinite resources (so as not to clutter up the user's playspace) and when a combination A+B->C should leave C in the place of A or B. The only part of the game that really encodes finiteness is mutual exclusivity.
   - Every composition has exactly one result. Multiple-result rules such as `A + B -> A' + B'` are not supported.
   - Composition rules are written "A + B -> C" or "A @ H -> C" or "A + B @ H -> C". Either or both item reagents can have an optional fate annotation immediately after their reference: `[consume]`, `[transform]` or `[preserve]`. For example, `A [transform] + B [preserve] -> C`, `A [transform] @ H -> C` or `A [transform] + B [consume] @ H -> C`. Annotations belong beside the reagents, not after the result. Preserve is the default if nothing else is specified, and you should omit `[preserve]` except when the single-use lint requires it: it's a lint error if an item is left un-annotated and is a reagent in only one composition in the story.
   - Warn when an item is marked `[preserve]` in some compositions but `[transform]` or `[consume]` in others. Apply defaults before comparing, so omitted annotations count as `[preserve]`; include implicit consumption from slot installation. Show the contrasting rules for author review. Uniform-fate editing options are choices, not proof that uniformity improves play; explain when implicit slot-owner preservation or component consumption prevents an edit while retaining the current slot structure. This detects mixed declarations; it does not establish whether every possible runtime retention decision is understandable.
   - Separate a fate annotation from the reference with a space, outside any quotes, bold, italics or backtick identifier. For a compound reagent, put it after the filled-slot reference: `A[B,C] [transform] + D [consume] -> E`. The attached brackets in `A[B,C]` describe filled slots; the separate `[transform]` annotation describes that reagent's fate in this rule.
   - When an item is transformed into a new item, details of its internal parts are lost: they don't remain separately labelled inside the result. The result has its own name and any explicitly declared slots. Installing a component into an existing compound item preserves its other filled slots.
   - Under hotspots, there's a shorthand "A -> C" stands for "A@H -> C", and "A + B -> C" stands for "A+B@H -> C".
   - Under an item, there can be nested sub-bullet composition rules. Each one must involve the item above it as a reagent (if the item was top level) or the result of the composition above it (otherwise). Alternatively, under an item or nested sub-bullet there can be as a shorthand one or more "+B -> C" or "+B@H -> C" or "@H -> C". These mean: combine with the thing produced on the previous line (or if the previous line was a top-level item then combine with it). Note that this is sequential. An explicit reagent can carry an annotation, as in `+ B [consume] -> C`. To annotate the implied reagent, write the full rule with its reference and annotation.
   - A composition rule can mark A or B with `[transform]` or `[consume]`. When composition happens that involves either fate, we look through all goals in current and future chapters, and all top-level items in future chapters (both taking into account mutual exclusivity) to be sure that the reagent isn't needed. If it isn't, we retain it in a hidden state, marked "transformed/consumed".
   - As an example, if a goal requires "either A or B" and there's a rule `A [consume] + B [consume] -> C`, then we have to consider the effect of marking them both as transformed/consumed.
   - The invariant which all the rules are aiming towards (and which we still have to prove is satisfied): no permitted choice or consumption ever removes the last viable continuation through the remaining chapter requirements at any stage.
9. Chapter needs and carry:
   - When you move to a new chapter, here's how we decide which items to populate it. Start with all items that are mentioned in top-level items or goals. This is our initial set of "needs". For every needed item, if currently exists as a standalone item then carry it forward into this chapter. A compound need "A[B,C]" if we have "A[B]" already only needs "C"; if we don't have anything then we need all of A,B,C. What might make a need not exist is (1) if it was never created, (2) if it was created but is marked as transformed/consumed.
   - If it doesn't currently exist, and isn't marked as transformed/consumed, then we need every reagent from every possible way to produce it (which aren't themselves marked as transformed/consumed), and if there are no rules that produce it then the item must be a primitive item itself which we need. The set of "possible ways" should respect mutual exclusivity of items and transformed/consumed items. It should be done by sets, since reagent dependents may have cycles: when unfolding reagents, skip expanding an item that has already been unfolded.
   - It's a corollary of the invariant that every needed item will be creatable by the player.
   - With that set of needs, divide it up into those items already present earlier in the story which go above the fold, and items not yet present which go below the fold. If we are inheriting hotspots, and the previous chapter had an item in the hotspot, then it will remain in the hotspot. If "A[B,C]" is a need and A exists, then put "A[...]" above the fold even if it's not yet complete.
   - Note: it's considered bad practice to have "new item primitives" (below the fold) in chapters that lack location images. These will be linted against.
   - The ways to combine items are (1) two items, (2) two items in a location, (3) one item and one location. The item specifications include in them all that's needed to know whether the combination results in items being discarded, preserved, created.
