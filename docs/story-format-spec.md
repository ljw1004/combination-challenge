# Story format specification

This document defines the Markdown language, game semantics and required diagnostics. Use the [authoring guide](story-authoring.md) for story design and the [README](../README.md) for repository layout and tools.

## Principles

- It should be easy to write+edit a story
- Although the notional model is that items are infinite, we nevertheless (1) "consume/transform" them, which doesn't truly consume or transform, but rather hides them from the game once a user would intuitively thing they'd go, (2) start fresh chapters with a smaller focused subset of items needed for the goals
- Although we focus on items needed for goals, we still want to allow "worldbuilding", allowing interesting constructions that feel rewarding even though they're not needed to satisfy any goals
- We want to ease the burden on authors: they should merely describe items, composition rules with intuitive consume/transform relations, new supply caches in chapters, and the engine should figure out all other details about which compositions truly will consume/transform something, which have to be left behind for further rules, which items will go into each fresh chapter.
- We use linters to guide authors away from likely defects, e.g. writing items that won't appear in game, or composition rules that are only possible under such narrow circumstances that they're probably not worth it, or misspelled references to items. These include defects that might arise from the implicit dependency behavior being subtle.

## Specification

1. Each file is a story. The filename of the story is ignored. The story has a heading and text, which will appear in the main menu of the game. The markdown may include `> NOTE:` quoted blocks, including at any indent level inside lists. These are comments for the story-author and have no effect on the game logic for the story.
   - A story's optional cover image is the very first paragraph of its description (between the title and first chapter), consisting solely of a Markdown image: for example `# Story\n\n![cover](assets/cover.webp)\n\nDescription.\n\n## Chapter 1`. Use the same standalone-image paragraph rule as chapter backgrounds. An image after earlier prose, an inline image, or an image sharing its paragraph with other content is not a cover. The description is preserved for catalogue display; cover selection does not remove authored text.
   - A new story first displays only its cover image (or the first chapter's background when no cover is declared) and a centered **Start** button. The cover is top-aligned; it does not add a title or caption. Relative cover paths resolve against the story Markdown location, like chapter artwork. Absolute HTTP(S) URLs are supported.
   - **Start** reveals the first chapter's normal background, items, goals and introductory popup. The cover does not create a game action or mark a chapter changed, and visiting it alone does not save a game. Existing saved progress resumes directly. **Restart chapter**, including chapter one, returns to that chapter's popup; **Restart story** returns to the cover. A cover image never replaces the required first-chapter background.
2. Each story is made up of a series of chapters, starting with `##`. The chapter has a name, used in the encyclopedia index and debugging tools. There is an optional final chapter, by convention named "The End", with no goals or hotspots or items. It's only role is to convey its chapter-describing popup as the final text of the story.
3. A chapter has an optional image, optional markdown paragraphs, and then sections "Goals", "Hotspots", "Items", "Combinations" each in bold with bullets under them. These sections may be omitted.
   - Image paths are relative to the story Markdown file.
   - The background cannot change within a chapter; a different background requires a new chapter.
   - Every chapter is shown to the user with an image. If the image is provided in markdown then the chapter's image is that and it carries over no hotspots; if no image is provided in markdown then the chapter's image is the same as that of the previous chapter, and it carries over the hotspots from the previous chapter. Note that the user might see two copies of the same image when they scroll back through their game's history.
   - How to distinguish the optional image? It will be the very first content of the chapter, and it will be in a paragraph with no other text after it. Thus for instance `## Chapter1\n![img1]()\n\n![img2]()\n` means that img1 is the background, and img2 is an image to display inside the chapter popup. It's not possible to have a chapter popup start with a "paragraph image" unless it has a background image.
   - If the optional text is present, then starting this chapter causes a popup text to appear. This text may include Markdown images, e.g. avatars of the philosophers.
   - There may be a paragraph of markdown which starts "[If skipped]". If the chapters goals were completed before it even started, then we skip the chapter, and accumulate these "if skipped" paragraphs into text of the next uncompleted chapter we land on (or dropped entirely if there isn't one).
   - Note that there's no such thing as "return to an earlier chapter". The chapters in a book are strictly monotonically increasing. It's possible for a later chapter to have the same image/hotspots as an earlier chapter, though.
4. Much of the markdown can refer to other things, especially goals, hotspots and items.
   - Only certain places in the grammar allow references, e.g. after "with" for items. Note that there are no places where we have prose that contains reference.
   - A reference can be enclosed in quotes, bold or italics to help it stand out, or it can also be just free text in places where the grammar is unambiguous about its start and end.
   - Every item and hotspot must have an explicit declaration somewhere in the manuscript. References resolve globally, including forward references into later chapters. A standalone non-recipe item bullet declares its plain-text identity; these entries are allowed in Items, Combinations and nested item lists, including beneath hotspots. A hotspot must have an entry in a Hotspots section. Declarations use the same quoting/emphasis rules as references. Recipe operands/results, goals, slot acceptances, filled-slot components, reading conditions, exclusions and `place:` targets are references, not plain-name declarations.
   - An explicit identifier-plus-display-name expression, e.g. `` `foo` Bar ``, declares that identifier even when embedded in a recipe or another item-reference position. A bare `` `foo` `` is only a reference and requires such a named declaration elsewhere. The same display-name requirement applies to hotspot identifiers, which also need a Hotspots entry. Refer to a backtick identity by its identifier, not its display name; `Bar` and `` `foo` `` are different identities. A `place:` target cannot declare an identity.
   - There is a single global namespace in the story for backtick identifiers, and a separate global namespace for non-backtick identifiers. If there are any clashes, then we take all references as referring to the first, and we lint against it.
   - For compound items, "A[B,C]" refers to an item A with at least slots filled with B and C. "A" is short for "A[]".
5. Goals has a bullet list of goals
   - Each goal has the form "Goal text" or "next: Goal text". The ones marked "next" will only be displayed when their immediate predecessor has been completed, and it's a lint error for the first goal to be "next".
   - A goal with exactly one condition may be written "Goal text -- Condition", including "next: Goal text -- Condition". This is shorthand for the same goal with Condition as its single sub-bullet. Any permitted form of goal condition may be used, including item, item @ hotspot, compound references and composition rules. An inline condition cannot be combined with sub-bullet goal conditions.
   - Each goal has one or more conditions (bullets). The conditions may have the form "item" or "item @ hotspot". If there more than one condition then they're taken by default as disjuncts. You are allowed to write explicitly "or:" in front of all items to show they're disjuncts, or "either:" for the first and "or:" for all the rest. Likewise you can write explicitly "and:" or "both:/and:". It's a lint error to combine disjuncts and conjuncts.
   - Conditions may also be writen "A + B -> C". This both declares a combination rule with the normal syntax, and also counts as an item goal "C". (Note: if there were another rule E+F->C in the story, then the goal could be satisfied by that construction too; if C already exists, then that will satisfy the goal). Composition conditions are not allowed to have sub-bullets under them (for follow-on compositions).
   - The goal "- A[B,C] @ H" means item A must have items B and C inside its slots, and be placed at hotspot H.
   - If there are multiple goals, they are by default conjuncts of goals. You can use the same "either/or/both/and" labelling in them. Within a `next:` chain, every goal remains required: a chain is complete only when all its goals have been achieved. The chapter's conjunct/disjunct combines these complete chains. `next:` controls sequential display, not which goals are required, and does not prohibit making a later result early; an already achieved later goal never bypasses an unfinished predecessor.
   - Once a goal is satisfied, it remains satisfied even if its witness later moves or transforms. For example, moving an item away from a required hotspot does not revoke the achieved goal.
   - Goal text is fixed: a goal such as "Cook X and Y" does not change to "Cook X" or "Cook Y" when one condition is satisfied.
   - Count visible goal chains by counting goals that are not marked `next:`. Up to two need no count acknowledgment. Three produce a warning unless the Goals section contains one hyphen (`-`) acknowledgment bullet with the exact text `(three goals are a lot but okay here because <REASON>)`, replacing `<REASON>` with a nonempty explanation. Wording, capitalization, punctuation and spaces in the fixed phrase are verbatim; ordinary Markdown indentation and whitespace after the bullet marker are allowed. The acknowledgment is author metadata, never a goal, item, condition or player-facing instruction. Four or more chains are a hard error that an acknowledgment cannot suppress. Use `next:` when sequential disclosure makes sense; every goal in its chain remains required.
   - Acknowledgments must be single top-level bullets without children or continuation prose. Empty/whitespace-only explanations, explanations containing the literal `<REASON>`, and duplicate acknowledgments are errors. An acknowledgment with fewer than three chains is obsolete and produces a warning with a removal fix. The three-chain warning's suppression fix inserts the exact template and selects `<REASON>`; the placeholder error persists until the author supplies a reason. The linter checks the explanation's presence, not its editorial merit.
   - Every nonblank Goals entry must parse as a normal goal, a condition sub-bullet, or the exact acknowledgment. Invalid goal forms and stray prose produce errors rather than being silently ignored. Normal goals require nonempty text and conditions; an inline form has exactly one `--` separator. Ordinary `> NOTE:` author comments remain excluded from parsing.
   - Warn when a goal pulls a primitive supply forward from a later Items listing. This is an author-review heuristic, not a chapter gate; see `future-supply` in the lint catalogue below.
6. Hotspots is a list of named hotspots
   - Hotspots may specify normalized image-relative coordinates: `- Signal mast (at 70%, 80%)`. Coordinates identify the hotspot centre, from the top-left of the chapter image, and must lie between 0% and 100%. Without coordinates, the UI uses its stable lower-panel layout.
   - A hotspot may have a direct child `icon: ![location](assets/mast.png)`, using the same path, quarter-size display, optional `(circular)` marker and conflict rules as item icons. It remains a fixed location, with its image centred on the authored coordinates. This metadata creates no item or recipe and does not require icons on other hotspots or items. A missing image falls back to the hotspot name. Document intended centres in author notes when generating background art.
   - A hotspot icon may be fully transparent when the background already depicts the location. Its intrinsic dimensions still define the displayed hit area; transparent pixels do not disable interaction, names or selection feedback. This uses ordinary icon metadata and adds no new placement or recipe semantics.
   - A hotspot may have direct children `place: Item (at 53%, 35%)`. The coordinates prescribe the item's centre in the same chapter-image coordinate space as hotspot centres. Item references use the normal identity and filled-slot syntax and must resolve to explicit declarations elsewhere in the manuscript, including later chapters. A `place:` entry never defines an item, supplies it, adds a recipe or adds a goal. All references inside it, including slot components, require their own declarations. Repeating an identical destination is permitted; conflicting destinations for the same item identity at the same hotspot are errors, including overlapping compound qualifications. The first applicable entry governs an incomplete preview. These entries belong to the hotspot identity and inherit with it.
   - On an ordinary drop at that hotspot, try the matching `place:` centre. Also try it for a newly created result of a hotspot operation, or a combination received by an item there, whether the player targets the occupant or the hotspot. Resolve the combination and its computed input dispositions before checking occupancy. The full measured result/item rectangle must fit inside its chapter panel without overlapping another available item there; exclude the moving item, retired inputs, background art and hotspot frames. Touching item edges is allowed. If the destination is occupied, cannot fit on the board, or has no matching entry, use the ordinary placement rules. Compound installation retains the owner's existing placement.
   - A prescribed centre must be inside the hotspot's hit area, including its boundary. This is a point check, not containment of the whole item image. Lint measures the actual text/artwork dimensions at the 390px reference width. A `(circular)` hotspot uses a centred circle with diameter equal to the smaller displayed image dimension, or 44px when larger; other hotspots use their measured rectangle with a 44px minimum icon hit area. Transparent artwork retains the applicable circle or rectangle. CLI geometry lint uses Chromium with the player's markup, CSS and artwork sizing; the live editor uses the same measurement and diagnostic functions. An unreadable geometry asset or unavailable CLI browser is a verification error, never a successful check. Out-of-range coordinates and outside-hotspot centres are errors. Invalid live drafts use ordinary placement instead of honoring an outside centre.
   - A successful authored placement establishes `@ H`, including a new result whose receiving ingredient survives. It remains freely reversible and applies on later drops even after a goal is achieved. It is not reapplied on redraw, resizing, reload, chapter carry or fitting a compound. Successful result placements are recorded with their combination for deterministic replay; failed/absent placement hints retain the ordinary result rules. Coordinates on goals or recipe references are invalid: hotspot coordinates belong on hotspot declarations, primitive starting coordinates on icon metadata, and destinations on `place:` entries.
   - It's a lint error to have hotspots without an explicit chapter image.
   - A hotspot can provide context for a two-item combination, act as the other operand for a one-item combination, or receive an item to satisfy a goal. Selecting a hotspot first considers legal contextual combinations with available occupants of that hotspot on that chapter panel. A unique match takes precedence over a one-item hotspot operation. With no occupant match, try the one-item operation, then ordinary placement. With multiple occupant matches, require a geometrically targeted compatible item; otherwise leave the incoming item in place and highlight the alternatives, never selecting by recipe order. The [UX drop-target rules](ux.md#work-surface-and-dragging) govern cursor/overlap geometry and priority between eligible items and hotspots. Hotspots never accumulate ingredients or capabilities of former occupants.
7. Items is a list of items
   - An item can have a wonder-description, one or more markdown paragraphs with optional pictures. These wonder descriptions will be popped up when the item gets created, and when the item is double-tapped (double-clicked on desktop). Holding an item does not open its reading.
   - You can nest items and combinations to show how one result can combine further. Shorthand omits repeated operands; it does not waive the declaration requirement for results or other references. An explicit standalone item declaration may itself be nested rather than top-level.
   - Item declarations, metadata and combinations are global. Repeated declarations of the same identity are permitted and union their facts across chapters, subject to conflict checks. Every referenced identity must have a declaration; a typo must not silently establish a valid new primitive or result. The parser may retain provisional identities in incomplete drafts for editable previews, but fast lint rejects missing declarations and deep validation waits until fast errors are resolved. Declarations with no references outside their declarations produce an author-review warning, not an error: a deliberately supplied worldbuilding item may be intentional. Producing a terminal result counts as a reference even if that result has no later use.
   - An item can be marked as exclusive with another, "- A (exclusive with B)". These markings must be mutual and pairwise. Exclusivity analysis checks goals and primitive chapter supplies; declarations of mutually exclusive derived items may coexist in Items. See the lint catalogue below for the precise diagnostics.
   - An item is **primitive** when no explicit combination produces it; implicit slot-installation rules do not make their owner derived. All other items are **derived**. An Items entry for a derived item defines metadata (including wonders and slots), without adding chapter needs or protecting ingredients against cleanup. Top-level primitive Items entries supply chapter needs, so put those entries in the chapters that should introduce the supplies; adding declarations must not gather all primitives into chapter one. Standalone declarations elsewhere establish identity without supplying it. Recipes and metadata remain global; their source chapter does not gate their use. Goal dependency expansion can still pull a declared primitive forward, with the existing `future-supply` warning where applicable.
   - An item can have an icon as a direct sub-bullet of a top-level Items declaration: `- Earth` followed by `  - icon: ![icon](assets/earth.png)`. Icon paths resolve relative to the manuscript, as chapter artwork does; absolute HTTP(S) URLs also work. The optional suffix `(circular)` selects a circular selection outline; otherwise the outline encloses the image rectangle. Images are authored at four times their display dimensions at the 390 × 844 reference viewport; other viewport sizes follow the [UX scene framing](ux.md#work-surface-and-dragging). Icon metadata does not create an item, wonder or combination, and does not change supply semantics. In particular, declare primitive icons in the chapter that should introduce those supplies; derived icon declarations do not add chapter needs. Repeating the same icon metadata is permitted; conflicting declarations are an error and the first remains authoritative.
   - A primitive item's icon may also specify its starting centre: `icon: ![water](assets/water.png) (at 70%, 80%) (circular)`. The `(at …)` and `(circular)` markers can appear in either order, at most once each. Coordinates use the same normalized, top-left-relative convention as hotspots and must be between 0% and 100%. They apply when that primitive first enters the game, using the displayed image dimensions to centre it; later movement, carrying, resizing and reloading do not reapply them. Authored positions reserve space during automatic arrival layout. Derived items cannot specify starting coordinates; their placement follows the creating combination. Slot overlays cannot specify starting coordinates, and hotspot centres remain on hotspot declarations. Invalid coordinates or derived-item positions are lint errors; incomplete live previews use automatic placement. Positions are presentation metadata and do not change the legal game actions.
   - Once any item or slot has an icon, every item identity and every declared slot must have one. Each item then needs a top-level Items declaration for its icon, even if its identity was declared elsewhere. An ordinary story with no icons keeps text presentation. Missing icon metadata is a lint error; a partial live-editor preview may still use text for those items.
   - Creating an item permanently rules out its mutually exclusive partner. Transforming or consuming the chosen item does not reopen the alternative.
   - An item can be marked compound, "- A (compound)". If so it has one or more slot declarations as sub-bullets, either "slot: Name, accepts Reference" or "unnamed slot: accepts Reference". The named slots will appear in the UI with ghost text. This notation only allows a single item to fill a slot. It's implicit that if A has a slot that accepts C, then "A[B] + C [consume] -> A[B,C]". It's a lint error if two slots accept the same item. Incidentally, both named and unnamed slots can be used in goals.
   - An icon-based compound supplies a base image with spaces for its fittings. Each slot appends its overlay to its declaration: `unnamed slot: accepts Window, icon: ![icon](assets/house-window.png)`. The overlay must have the same pixel dimensions as the owner's base icon, with transparent padding to align the fitted part. Draw the base first, then filled slots in declaration order, from back to front: a later-declared slot paints over an earlier one wherever they overlap. This order is guaranteed regardless of the order the player fills the slots, including after reload. Declare rear fittings before foreground fittings. Slot icons describe fitted appearances; the accepted item also needs its own standalone icon. Icon compounds show only the base item's name badge; [UX](ux.md) owns interaction and presentation.
   - A compound item can have a wonder markdown, meaning it will be shown when the basic item exists. Or the wonder markdown might start with "[B,C]" indicating that the wonder text will appear the first time slots have been filled. In this case, double-tapping only shows the wonder text after those slots have been filled.
   - An item declaration can be written "A (or from chapter X, B)" to indicate that once the player reaches chapter X from then on the item will be named B instead. This applies everywhere, including when scrolling back to earlier chapters. For example, adding "Augustine:" helps the player distinguish an earlier claim after encountering other thinkers; returning to the old chapter does not restore the shorter name. Note there's no equivalent facility for wonder-popups on items; that would break continuity. The change in label is to help the user orient themselves, but the expansion into a popup should feel more solid like a permanent record.
8. Combinations. These are lists of combinations, similar to items. They allow nesting just like with items.
   - Exactly one authored combination in each manuscript must end with the unquoted marker `(tutorial)`, separated from its result by whitespace: `A + B -> C (tutorial)`. The marker is metadata, never part of the result name or logical recipe identity. It is accepted wherever an explicit combination is allowed, including nested/shorthand rules and goal conditions. Repeated declarations and repeated markers count separately even when their logical recipes deduplicate. A quoted item name containing `(tutorial)` remains an ordinary name.
   - The marked declaration must be in the first chapter and must execute immediately from the initial game state, without making ingredients or preparing a receiving placement first. Its authored first ingredient is the drag source, and its second ingredient is the receiving target; for a single-item hotspot operation, the hotspot is the target. The shared engine must select that marked recipe for this directed action. The marker neither supplies ingredients nor changes gameplay eligibility, goals or result visibility. See [UX](ux.md#contextual-tutorials) for the tutorial's presentation and completion rules.
   - Although we say that some reagents are "consumed" or "transformed", they really aren't. Every item in the game is really an infinite resource. The words "consume" and "transform" are hints to the engine about when to hide these resources to reduce clutter. The final computed dispositions determine result placement under the [UX matrix](ux.md#result-placement). The only part of the game that really encodes finiteness is mutual exclusivity.
   - Every composition has exactly one result. Multiple-result rules such as `A + B -> A' + B'` are not supported.
   - Composition rules are written "A + B -> C" or "A @ H -> C" or "A + B @ H -> C". Either or both item reagents can have an optional fate annotation immediately after their reference: `[consume]`, `[transform]` or `[preserve]`. For example, `A [transform] + B [preserve] -> C`, `A [transform] @ H -> C` or `A [transform] + B [consume] @ H -> C`. Annotations belong beside the reagents, not after the result. Preserve is the default if nothing else is specified, and you should omit `[preserve]` except when the single-use lint requires it: it's a lint error if an item is left un-annotated and is a reagent in only one composition in the story.
   - Warn when an item is marked `[preserve]` in some compositions but `[transform]` or `[consume]` in others. Apply defaults before comparing, so omitted annotations count as `[preserve]`; include implicit consumption from slot installation. Show the contrasting rules for author review. Uniform-fate editing options are choices, not proof that uniformity improves play; explain when implicit slot-owner preservation or component consumption prevents an edit while retaining the current slot structure. This detects mixed declarations; it does not establish whether every possible runtime retention decision is understandable.
   - Separate a fate annotation from the reference with a space, outside any quotes, bold, italics or backtick identifier. For a compound reagent, put it after the filled-slot reference: `A[B,C] [transform] + D [consume] -> E`. The attached brackets in `A[B,C]` describe filled slots; the separate `[transform]` annotation describes that reagent's fate in this rule.
   - When an item is transformed into a new item, details of its internal parts are lost: they don't remain separately labelled inside the result. The result has its own name and any explicitly declared slots. Installing a component into an existing compound item preserves its other filled slots.
   - Under hotspots, there's a shorthand "A -> C" stands for "A@H -> C", and "A + B -> C" stands for "A+B@H -> C".
   - Under an item, there can be nested sub-bullet composition rules. Each one must involve the item above it as a reagent (if the item was top level) or the result of the composition above it (otherwise). Alternatively, under an item or nested sub-bullet there can be as a shorthand one or more "+B -> C" or "+B@H -> C" or "@H -> C". These mean: combine with the thing produced on the previous line (or if the previous line was a top-level item then combine with it). Note that this is sequential. An explicit reagent can carry an annotation, as in `+ B [consume] -> C`. To annotate the implied reagent, write the full rule with its reference and annotation.
   - A composition rule can mark A or B with `[transform]` or `[consume]`. When composition happens that involves either fate, we look through all goals in current and future chapters, and top-level primitive items in future chapters (taking mutual exclusivity into account) to be sure that the reagent isn't needed. Derived Items declarations do not add protection. If the reagent isn't needed, we retain it in a hidden state, marked "transformed/consumed".
   - For a new result from a two-item combination, use the actual receiving item's chapter. If the receiver is retired after protection checks, the result inherits its hotspot placement too. A surviving dragged input retains its source placement. Compound installation retains the owner's placement. The [UX matrix](ux.md#result-placement) owns pixel placement for the final computed dispositions; recipe operand order does not determine the drop destination.
   - As an example, if a goal requires "either A or B" and there's a rule `A [consume] + B [consume] -> C`, then we have to consider the effect of marking them both as transformed/consumed.
   - The invariant which all the rules are aiming towards (and which we still have to prove is satisfied): no permitted choice or consumption ever removes the last viable continuation through the remaining chapter requirements at any stage.
9. Chapter needs and carry:
   - When you move to a new chapter, here's how we decide which items to populate it. Start with all items that are mentioned in goals, or are top-level non-derived items. This is our initial set of "needs". For every needed item, if currently exists as a standalone item then carry it forward into this chapter. A compound need "A[B,C]" if we have "A[B]" already only needs "C"; if we don't have anything then we need all of A,B,C. What might make a need not exist is (1) if it was never created, (2) if it was created but is marked as transformed/consumed.
   - If it doesn't currently exist, and isn't marked as transformed/consumed, then we need every reagent from every possible way to produce it (which aren't themselves marked as transformed/consumed), and if there are no rules that produce it then the item must be a primitive item itself which we need. The set of "possible ways" should respect mutual exclusivity of items and transformed/consumed items. It should be done by sets, since reagent dependents may have cycles: when unfolding reagents, skip expanding an item that has already been unfolded.
   - It's a corollary of the invariant that every needed item will be creatable by the player.
   - With that set of needs, divide it up into those items already present earlier in the story which go above the fold, and items not yet present which go below the fold. If we are inheriting hotspots, and the previous chapter had an item in the hotspot, then it will remain in the hotspot. If "A[B,C]" is a need and A exists, then put "A[...]" above the fold even if it's not yet complete.
   - Note: it's considered bad practice to have "new item primitives" (below the fold) in chapters that lack location images. These will be linted against.
   - The ways to combine items are (1) two items, (2) two items in a location, (3) one item and one location. The item specifications include in them all that's needed to know whether the combination results in items being discarded, preserved, created.

## Lint rules

This catalogue owns the purpose and exact trigger of each diagnostic. “Error” rejects a manuscript; “warning” requests author review. Syntax and deterministic model checks run in the fast stage. Global checks run in the deep stage only after fast errors are resolved. Diagnostics point to the offending source span; related locations explain conflicting declarations or dependencies. CLI-only artwork checks additionally inspect the filesystem. A diagnostic about an analysis limit is a failure to complete verification, never a finding that content is unreachable.

### Syntax and declarations

All rules in this table are fast errors.

| Code | Motivation | Formal condition |
|---|---|---|
| `missing-title` | Give the story a player-facing identity. | No `# ` heading occurs before the first chapter. |
| `missing-chapters` | Supply a playable story structure. | Parsing produces zero `## ` chapters. |
| `tutorial-count` | Give every story one unambiguous opening demonstration. | There are zero or more than one authored `(tutorial)` markers. A missing marker points to the story heading; each extra marker points to its own span and relates to the first. Duplicate recipe declarations still count separately. |
| `tutorial-chapter` | Teach dragging at the start of play. | An authored tutorial marker occurs outside the first chapter, regardless of where the same global recipe was first declared. |
| `empty-reference` | Prevent unnamed identities. | A reference has an empty name after stripping permitted wrappers and qualifiers. |
| `identifier-clash` | Keep explicit identity unambiguous. | The same backtick identifier has two different declared display names; the first remains authoritative. |
| `undeclared-item` | Reject misspelled names before implicit preview supplies can disguise them as valid items. | A plain-name item reference has no standalone item declaration anywhere in the manuscript. Check every authored occurrence, including results, slots, readings, exclusions and placements; forward declarations are valid. Highlight the exact reference, not its surrounding row. |
| `undeclared-id` | Resolve backtick identities to explicit names. | An item identifier has no identifier-plus-display-name declaration as an item, or a hotspot listed in Hotspots lacks such a declaration as a hotspot. Bare identifier listings and same-text plain names do not satisfy this requirement. Report each authored occurrence. A hotspot without any Hotspots entry instead receives `undeclared-hotspot`. |
| `coordinate-context` | Keep coordinates attached to their intended declaration. | A coordinate suffix occurs on an item/hotspot reference rather than a Hotspots declaration, primitive icon or `place:` entry. |
| `place-context` | Give placement metadata a clear owner. | A `place:` entry is not a direct child of a Hotspots declaration. |
| `place-syntax` | Give each destination a reference and centre. | A placement is not `place: Reference (at X%, Y%)`, carries item-declaration qualifiers, or has nested bullets/prose. |
| `place-position` | Keep centres in the chapter image. | Either placement coordinate is nonfinite or outside 0%–100%. |
| `conflicting-place` | Avoid order-dependent destinations. | Two `place:` entries for the same hotspot and item identity have different coordinates, regardless of slot qualifications. |
| `multiple-exclusions` | Keep exclusivity pairwise. | One item is explicitly assigned two different exclusive partners. |
| `icon-syntax` | Make icon metadata unambiguous. | An icon declaration is not `icon: ![alt](nonempty-path)` with optional trailing `(circular)` and `(at X%, Y%)` markers in either order, a marker is repeated, or an item/hotspot icon has nested bullets or prose. |

### Opportunities for authored content

**Motivation.** Following the [principles](#principles), optional worldbuilding is welcome and the engine manages dependency details. This check helps authors avoid fruitless work: constructions whose ingredients never coexist, or that require a narrow combination of earlier leftovers. A recipe graph alone is insufficient because cleanup, installation, chapter carry and exclusivity affect availability. The check deliberately errs towards flagging fragile opportunities. It does not measure how frequently human players would find something.

**Gameplay and authoring analysis.** Gameplay seeds chapter needs from goals and top-level primitive Items entries, expands the global recipe dependencies, and applies the actual state's carry and cleanup rules specified above. Derived Items entries provide metadata without adding needs. The linter uses these shared operations to assess optional content, then deliberately compresses alternative histories. Its pessimistic summaries and 100-element limit apply only to authoring analysis; they do not determine the player's actual inventory.

The calculation has four steps: build complete sets of goal dependencies; evaluate each set once through the shared engine; probe optional constructions locally without adding them to goals; and merge chapter endings pessimistically before advancing. The definitions below specify each step.

**Authoring criterion.** Every item should have an opportunity under the construction-set calculation below; otherwise emit an author-review warning. Previous chapters contribute goal-directed work alone. An optional preparation in an earlier chapter cannot be required to establish an opportunity. Fetching objects or using hotspots from scrollback is excluded even though the game permits it. A warning means failure of this pessimistic authoring criterion, not proof of absolute impossibility or rejection of the manuscript. Optional content remains permitted; authors are not required to make it a goal or guarantee its survival after discovery.

**Logical state.** Retain item creation/availability/retirement, installed components, qualified slots, exclusions, goal latches, chapter membership, hotspot placement, visited chapters and completion. Dismiss readings automatically. Ignore pixel coordinates, UI bookkeeping and action history: those do not affect the permitted logical actions. Preserve the difference between an uncreated object and a retired object; retired results cannot be created again.

**Construction sets.** A construction fact is either a newly created item identity or a filled slot on an owner. For an arrival state `s`, a reference already available on the current board requires the empty construction set. Otherwise expand its possible producers backwards through their operand references, adding each producer's result facts. Installation requires the owner and component and adds the owner-slot fact. Reject unseeded cycles, incompatible exclusive identities, unavailable hotspots and attempts to recreate an existing identity. Conjunction takes unions of prerequisite sets; disjunction takes alternatives. After every operation, deduplicate by the set of construction facts, merging producer recipes and selected goal conditions for identical sets. Thus eleven independent goals with one construction each yield one set of eleven facts, not 2,048 partial inventories. Different intermediate constructions still yield different sets.

Let `G(c,s)` be the resulting family for chapter `c`'s unfinished goals. Conjoin every goal in a `next:` chain, then combine chains using the chapter's conjunction/disjunction. Within a goal, use its condition conjunction/disjunction. Goals already latched at entry contribute the empty set. Selecting one goal alternative does not also authorize constructing its unused alternative. Let `T(i,s)` be the corresponding family for constructing item `i` alone.

**Evaluating a set.** Maintain one working logical state per construction set. Repeatedly perform selected goal placements that are possible, then the first legal producer that adds an unbuilt required fact. Order producers by decreasing number of result facts, then source line and recipe ID. Use the shared game engine for actual actions, cleanup, installation, goal latching and exclusions. Placement is limited to selected current-goal conditions or positioning a receiver immediately before a contextual combination. Do not branch over action orderings, receiver choices or subsets of completed constructions. Reject a set if evaluation stalls; for goal-only evaluation, also reject it if the chapter completes before all its planned constructions are built. A qualifying ending has built the entire set and completed the chapter. This deterministic evaluation can reject an order-sensitive opportunity; the authoring check deliberately does not search for a favourable ordering.

**The set of sets and OPTIONAL retirement.** Merge histories under either of two grouping rules. Construction grouping requires the same relevant created identities, qualified slots, exclusions, future goal latches and visited chapters; possible retirement and placement are recorded independently and collapsed pessimistically as below. Inventory grouping requires collapsed states to agree on every available or installed token, including slots, chapter membership and meaningful hotspot placement, and on exclusions, future goal latches and visited chapters. Inventory grouping discards distinctions between previously retired and never-created intermediates; it keeps differing live inventories such as a radio route and a beacon route separate. After a merge, collapse and repeat either grouping rule until no further match remains, preferring construction grouping when both match. Do this as endings and arrivals are inserted, before checking frontier width. No representative playthrough or Cartesian expansion is selected.

**Creation uncertainty.** For each relevant identity, retain a creation blocker if any merged history records it as created. If another history allows it never to have been created, additionally record that possibility in an independent set `U`. Merge these possibilities by union, including uncertainty inherited from earlier merges. A retired-versus-uncreated item is unavailable and blocked from recreation in the construction/carry state. Its earlier discovery remains credited. Preserve `U` through subsequent chapters; converting it into a plain retired record would lose information needed by cleanup.

**Cleanup with uncertainty.** For a retirement query only, copy the construction state and remove the historical token records in `U` before running the shared continuation checker. This allows their never-created possibilities to supply future alternative recipes in that query. It neither makes them usable as current ingredients nor supplies them on the next board. Definitely retired items remain retired. This distinction matters because removing a future alternative can otherwise invent protection for another ingredient: the engine might retain it solely because pessimistic merging removed its substitutes. Recipe matching, exclusivity checks and chapter advance still use the construction state; only the retirement query uses this additional possibility information.

An evaluated ending alone does not determine retained inventory. To assess possible retirement without enumerating orderings, take its completed constructions and goal latches, and make the set's newly constructed resources and its entry-available resources available in an assessment state. Do not restore resources already retired at entry. For each consuming/transforming operand in any merged producer, use the uncertainty-aware retirement query above to ask whether removing that operand alone permits continuation. If so, mark it retired in the ending (installed for component installation). Retain any retirement that actually occurred during evaluation. Assess operands independently: jointly pessimistic retirements may describe no single real playthrough. This deliberately discards protection arising only from an incidental evaluation order.

At a chapter boundary, collapse each group into **one** state. A relevant item with a consumed/transformed possibility becomes retired; otherwise an installed possibility becomes installed. Conflicting chapter locations become old-board locations; conflicting hotspot placements become unplaced. Unspecified receiver placements from contextual combinations are also unplaced; selected goal placements are retained only when they agree. Do not expand OPTIONAL records. Collapse before calculating next-chapter needs and carry. Created identities remain recorded, so retirement never permits resupply or recreation. Exclusions continue to follow created identities, including retired items. Incompatible exclusive constructions remain separate frontier elements.

**Local opportunities.** For each uncertified derived item `i`, evaluate `T(i,s)` on the current board, without advancing. If it is still uncertified, also evaluate unions of its target sets with sets in `G(c,s)`, allowing useful current-chapter goal work. Use the same evaluation procedure, but allow work after chapter completion while still on that board. Keep the actual goals unchanged: making the optional target a goal could protect its ingredients and fabricate an opportunity. An optimistic recipe closure may rule out a target; membership alone never certifies it. Local-probe results never seed later chapter histories.

**Formal acceptance.** Let `F(c)` be chapter `c`'s grouped frontier, `C(h)` the single pessimistic collapse of group `h`, and `U(h)` its persistent possible-noncreation set. Let `L(c,s,U)` be the identities created in `s` or during any evaluated goal/target set's permitted prefix, using `U` for retirement queries. Begin with the actual initial arrival and empty `U`. For each `h` in `F(c)`, evaluate `G(c,C(h))` with `U(h)`; assess retirement in qualifying endings, group compatible endings, collapse each, and apply the actual engine's advance, including skips, to populate later frontiers while preserving creation uncertainty. An item passes iff it belongs to `L(c,C(h),U(h))` for some chapter `c` and some `h` in `F(c)`. A completed arrival additionally certifies identities present there. Failed evaluations can certify discoveries made before they stalled, but cannot supply chapter endings.

This is a deliberately pessimistic authoring model for cleanup, not an exact enumeration of real histories. It may lose a construction that requires a particular earlier retention outcome. Independent retirement choices need not describe one actual prior playthrough; the check must not present these abstract histories as replay witnesses. Small regression fixtures can demonstrate actual gameplay routes alongside their stricter lint outcomes.

**Reduction and limit.** Old facts may be ignored only when they cannot affect any current or future permitted action. The implementation retains a conservative dependency cone containing future goal/supply ancestors, optional forward constructions, current-board extras and slots, and identities that can block creation through exclusivity or containment. Old hotspot placements are discarded when no future active surface or goal can observe them. Cleanup reads future requirements, so a material history fact need not be a current recipe operand. Stop as soon as any family of distinct construction sets or chapter frontier exceeds **100 elements**. The cumulative number of sets evaluated across chapters/arrivals can exceed 100; that is different from the width of any one family. Engine operations update a set's one working state and are not additional search states.
