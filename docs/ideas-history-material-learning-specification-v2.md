# Settled integration specification candidate: build, teach, host

26 October 2026. **Prospective specification, not authorization or evidence of an integrated game.** Reconciles the first adapter proposal with the opposed-view controls. ## Finite purpose collection, not copied demo counts

One constructed site has three linked purposes:

1. **Useful working observatory:** a functioning garden and player-built supported apparatus make actual scientific records. Use the settled physical scenario's laws, not fabricated completed artifacts.
2. **A chosen live standpoint:** residents choose a calibrated optical origin and ask to look in different directions without silently moving their standpoint. The later service concerns current faithful views, not stored records. The origin is player-selected among legal positions; replacement at that origin remains legal. If the desired service is merely two-front comparison, different-center cameras are valid and this stronger panorama purpose must not be imposed.
3. **A learning civic host:** a learner receives demonstrated controls and actually hosts requested views using those same built parts under a bounded resident mandate while its creator pursues another role. Human operation remains a legitimate service alternative, but does not itself enact the chosen learning-host project.

These are different purposes on one state, not an action estimate. A robust static layout may make operation easy; retain it. The endpoint must not require all offered concepts, a particular camera ID, a hinge, a refusal demonstration, or reproducing every old research goal.

## Exact controller vocabulary

The physical adapter uses only actual `move`, `hinge`, and `connect` actions. No known-design instantiation, synthesis, attachment, transformation, demolition, copying or record creation is performed by the controller. Player construction remains unrestricted under the ordinary laws. This is an explicit narrow operating mandate, not a claim that future machines can never build.

A method is a request guard plus an exact demonstrated action list on bound actual objects/parts. Guards can read the requested target and a pure current faithful-view relation. They cannot read completion flags, the hidden solution or cached old success. For this first candidate, no automatic generalization to a new physical binding occurs.

Default invocation:

1. If a faithful current view for the requested target already exists at the chosen viewpoint, report that relation and perform no control action.
2. Otherwise choose the player's explicitly taught matching method, validate its bindings/mandate, and replay its demonstrated actions through the ordinary physical transition function.
3. Stop on the first rejected internal action, exposing the actual accepted prefix. Re-evaluate current view and continuing service using the resulting world. Never assign success from the demonstration's old outcome.

When several methods match, the player's explicit selection or disclosed priority determines the choice; there is no secret planner. Whole invocation is one selected intervention; internal physical transitions have a separate automatic ledger. Exact previews must match prefix failure and all physical consequences.

## Required controls before choosing implementation

1. **Static rich apparatus:** allow every legal camera/plate/clear boundary and all known methods. Distinguish fixed layout from fixed pose; the perpendicular dual-plate method still rotates a lens.
2. **Different-center fixed cameras:** retain the four-operation opposed-view workaround where the chosen purpose permits it. Common viewpoint must follow the requested experience, not a hidden anti-shortcut rule.
3. **Whole-camera half-turn:** preserve the simple reusable controller and direct human operation.
4. **Previously recorded views:** prove live relation is unaffected by record novelty, without mutating any record.
5. **Changed real geometry:** a later human relocation/obstacle can invalidate a plan; test truthful failure and recovery, but do not insert compulsory sabotage into the player scenario.
6. **Current sources:** disconnected power/water, unsupported moved parts, changed local joints and ray obstruction remain effective. No actor learning grants immunity.
7. **Knowledge versus actual device:** copying the method does not copy apparatus, personal experience, physical support, active contact or past records.
8. **Short-route and count audit:** one invocation remains one choice even if it runs multiple physical transitions. No former session, source-exposed screen or automatic cue contributes to the new player's count.

## Falsifier and decision

The mechanical gate is that the actor's new method genuinely operates the built creation through the same laws, with exact observable current consequences. The experiential question is whether making that creation teachable and useful to another participant is worth doing.

Negative outcomes include a trivial target→pose lookup wrapped in clerical teaching, redundant demonstrations after static construction already solves the actual purpose, unused prerequisite unlocking, or apparent value caused only by deliberately awkward manual controls. A legal short universal method is not automatically negative; a player may value clear competence. No amount of recipe length settles the question.

Select bounded integration implementation only after the physical pilot's independent interpretation and agreement on the complete purpose/adapter contract. Build executable whole-collection and generous-shortcut witnesses under that implementation before freezing source, all purposes, alternatives, count semantics and neutral assignment for any new player. This specification does not start another microvariant pilot and does not claim the approximately-200-decision destination.
