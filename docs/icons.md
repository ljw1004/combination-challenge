# Goal: icons for "Elements" story

I want the Elements story to be played with icons, not text boxes. I want a nice recognizable icon set that lets people achieve the same quick recognition as the current text boxes. I want it to have an icon style that's consistent, and which doesn't look too "samey" compared to the mass of iPhone games with cutesey graphics, and which doesn't look AI-generated.

I've purchased/downloaded some other example icon-sets in the references/icon-sets directory. All have licenses that would permit us to use them. We don't have to use them. They are there just as ideas and inspiration, for instance in case we need inspiration on what kind of icon might represent say "pickaxe". For "Elements" story, I think the feel I'd go for is outdoor survival or subsistence, like primitive humans, or like someone fending for themself in the wildrenss. The fire in our story is like a campfire or a low-tech forge. There are some which are so abstract (air, water) that we'll naturally have to go more abstract for those.

I've also written out some completely different approaches in the references/icon-sets/art-styles directory which take us away from conventional video games into something with more soul. I don't know which I'd pick.

An icon will be written under a top-level item declaration as `- ItemName\n  - icon: ![icon](url)`. For compound objects, the icon should contain appropriate blanks for slots, and each slot must have `, icon: ![icon](url)` after saying what it accepts. The slot icons will be of the same dimensions as the base icon, with transparency, so they can be compounded. Within a story, for consistency, we'll add a lint error if some items/slots have icons but there exist other items/slots without them. This means that icon-based stories will need every item to have a top-level declaration; for primitive icons these will typically be written in the chapter where they're intended to be introduced (not earlier since that would introduce them earlier), and derived icons can be declared anywhere but they're typically declared in the first chapter that has rules that result in them.

What would the icons look like? Icons are supplied at 4x their intended display dimensions, hence a WxH pixel icon will occupy W/4xH/4 CSS pixels onscreen. (This is assuming the 390px reference width; if screen space is limited then the icons will be scaled)
- If we pick traditional game icons, then I guess they'd generally be 224x224 PNGs with the icon, and partially opaque black to make a circle around it, and a faint outline, and fully transparent outside that circle. I imagine that compound objects would typically be rectangular.
- If we pick something different like woodcut or medieval, then I guess they'd usually be sort of rectangular, might include a hand-made border in the image, perhaps slightly irregular with transparency around it.
- If we pick non-uniform sized icons like risograph, well, any size! I imagine there wouldn't be partially opaque black everywhere, but there might be an irregular border around the image so it still looks clear.
- For slots of a compound object, they'll overlap directly on top of the base image, so they should have padding to keep alignment.

When you pick up or touch or drag an item, then it will display the name of the item in a rounded-rectangle badge just below the icon circle, touching it, white sans-serif text, with faint outline black partial opacity. It will likewise display names of all other highlighted "possible co-reagents" in the same way. For compound items, the nametag will only be that of the base item, not its slots. The dotted rounded-rectangle border that we display around objects when you select them will be be around the full PNG width. Exception: if the icon was declared as `icon: ... (circular)` then it will be a dotted circular border within the icon's dimensions.

How to generate a huge number of icons with a consistent visual style and language, where all are easily recognizable? I have no idea. It will be a challenge. You're welcome to come up with your ideas. Here is one possibility:
- Provide a short style guide covering silhouette, line weight, palette, perspective, texture and visual scale.
- Provide small, fixed set of approved reference icons, supplemented by related objects when generating a family.
- Maybe we'd have the image generator produce a whole contact sheet of icons at a time? or just one at a time?
- When we generate icons we'll have to be careful to give context, e.g. if we merely told it "Earth" then it might produce images of the planet Earth, whereas what we want is soil. I imagine one way to provide context is to give the generator the chapter's introductory text where the icon first appears, and maybe also tell it about some combinations involving the icon (both producing it and using it). We could also provide it with story context, e.g. "Earth: loose soil; distinguish from sand, clay and stone".
- Maybe we'd have an "icon reviewer" where we give an individual icon to a fresh subagent and ask what it that icon is. Or if it's struggling then we might give it the chapter introductory text as context. We'd keep track of how many got it right on a "blind" guess, and how many got it right on the guided guess, and how many failed. If it can guess what the thing is, then good. We should be careful to allow close matches, for instance if it guesses "soil" then we should count that as a win for our item "earth".
- We should probably generate a small set first, to check that we've got a good process, and tweak our process if it's not working. Here's what might go in a small set, to span the range: telescope, pendulum, clockwork, botanical drawing, bread, porridge, feast table, cider, brick, iron, thread, brine, smoke, earth, air, plant, flower, house, window, sleeping-mat
- We will create a few versions of an icon-test story, with the above images, in different art styles (riso, woodcut, medieval, traditional-game, japanese-edo, diderot)
