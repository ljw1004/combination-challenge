# A challenge after recipes become inspectable

Research return: 25 October 2026. This revisits original designer passages after the tactile-table experiment and the owner's praise for hover discovery. It supplies predictions for the next experiment; the proposed tests below have not been run by this research pass. Existing evidence is recorded in [hands-on-iteration.md](hands-on-iteration.md), and the current constraint is in [design-contract.md](design-contract.md).

**Subsequent user correction:** finite physical materials and stock management are rejected. The allocation proposal and finite-pool comparisons below are retained as historical research, not current recommendations. All known materials remain permanently available; no resource, copy, budget or hidden-cost substitute may restore the rejected scarcity. The next geometry screen must use unlimited copies. An awkward compound can be set aside, so it is never a globally lost session: only that compound's ability to extend into the target can be blocked. If unlimited copies remove the worthwhile spatial choice, discard this candidate instead of restoring scarcity.

**Current recommendation:** test geometry with unlimited material access. Process/order remains a separate possible experiment only if it creates a worthwhile combination decision without stock management or compulsory waiting. None is established as enjoyable.

The question is whether an informed player has something worthwhile to work out or perform. Hover information has earned protection through actual owner feedback. An AI player's preference for less information is not a vote that cancels that evidence. The slight confusion about which icon displays an outcome can be addressed while preserving the information.

Two tensions matter. Barth values construction without prescribing a solution, while Teikari sometimes designs around a required interaction. Both accounts can motivate an experiment. Therefore **multiple viable plans is a diagnostic for an expressive-choice claim, not a universal law of fun**. A brief, unique-solution puzzle may still offer a nonobvious composition. It fails here when exposing its recipes leaves only the physical execution of an obvious chain, or when every purportedly fresh encounter repeats the same solved relation.

Koster's information-progress account also differs from the owner's preference for knowing local combinations. The intended remaining uncertainty concerns a plan's usefulness or the player's performance. We should not restore uncertainty about the authors' vocabulary to satisfy a generic curiosity metric.

## What full information means

For these screens, all ingredient compatibilities, immediate results, resource costs, conditions and consequential scheduled events are public. Hover/contact remains a local way to inspect them. Do not hide a second reaction catalogue behind “freshness,” add an unexplained exception, or require memorizing which of several visually identical mixtures carries a secret history.

This is not an automatic display of the optimal future policy. Knowing the legal transitions can coexist with having to compose them into a plan. Conversely, making the state large enough to defeat an exhaustive solver is not a design achievement by itself. The small screen should make the remaining inference identifiable.

Keep the gestures stable: pick up an actual thing, bring it to another thing or joint, inspect the consequence, release, then handle the result. A goal can be visible without becoming the primary control. A menu selection that orders a machine or character to perform the joins does not test the owner's desired experience.

## Three candidates and their rejection tests

### A. Finite ingredients with competing uses — rejected by user constraint

**Small playable question:** given a handful of physical pieces, how should their shared ingredients be committed to useful results? Put the remaining copies on the shelf itself. At least one intermediate must be usable in two consequential ways. The screen needs one visible problem and its consequences, not a request list plus an inventory dashboard.

**Prediction with all recipes revealed:** a public change in the situation changes which use of the shared intermediate an informed player prefers. The player can explain the change by its consequence rather than by learning a newly permitted pair. At least one plausible early commitment should allow a different, somewhat costly completion rather than secretly dooming the entire session.

**Tiny experiment:** freeze a small graph and initial stock. Construct six matched context pairs, changing one need, spatial relation or deadline within each pair. Twelve cases is a screening convention, not a sample of human enjoyment. Compare uniform legal actions, an immediate-payoff heuristic and a bounded planner with the same public rules. Save a choice where an intermediate can serve two roles. Replay both continuations and identify the relevant resource/capability difference. Also run an unlimited-stock control: if nothing changes, scarcity is probably decorative.

Normalize solutions before crediting diversity. Swapping independent joins, using a different copy of an identical ingredient, or producing the same final capability through renamed equivalent objects does not create another mechanism. Distinct resource allocations can be real alternatives, but the report must say what one sacrifices for the other. Changing numerical reward weights can create a preference reversal by construction; include a contextual change that affects causal usefulness, so the screen does not only demonstrate reading the larger number.

**Strongest reason to discard:** it becomes a shopping-list or key puzzle. The objective fixes a mandatory recipe multiset, and the player's work is tracing prerequisites and preserving exact counts. Extra scarcity makes misclicks expensive without adding an inference. If this is what the cheap screen reveals, do not rescue it with more recipes, currencies or hidden downstream demands.

**Tangible-performance check:** the player should actually consume and fuse their chosen pieces. Requiring repeated shelf retrieval of a long solved prerequisite chain is still work even when every drag is faithful. Track those chains as possible chores, not as engagement.

### B. Processes, order and conditions

The [Laudan return](transformations-and-ideas.md) suggests treating a material's transformation history as consequential. Her historical account does not validate a game mechanic and does not require retaining fermentation as the theme.

**Small playable question:** take the same visible mixture toward an immediate use or a developing intermediate. A living mixture, for example, could be heated now for one immediate portion or kept active to prepare another portion later. Every condition is visible on the changing object. Warmth/contact is performed by handling the vessel or material, not selecting a process from an apparatus dashboard.

**Prediction with all conditions revealed:** a visible near need favors the immediate use; enough preparation room favors keeping the intermediate active. Players predict how a chosen contact changes what the mixture can later do. At least one process can be interrupted or redirected usefully. A different preparation order matters through its effects, not because the author designated one correct ritual.

**Tiny experiment:** two preparation routes, one persistent process state, two forecast schedules and one scarce shared input. Replay the same stock against both schedules; record the earliest point the preferred order differs. Compare with a fixed-pair model that collapses the process state. Count only changes that alter a useful capability or recoverable decision. Try a plausible premature heating action and show whether recovery exists. No wall-clock waits are necessary for this screen; if time advances on joins, expose that rule and inspect its perverse incentives separately.

**Strongest reason to discard:** it is one mandatory sequence with animated waiting, or it hides an exception behind temperature/history bookkeeping. “First do A, then B, then C” with known outputs is not a new challenge merely because it takes time. Automatic progress, a wait button or more realism cannot by themselves turn that script into a choice.

**Tangible-performance check:** show the thing changing where it is being handled, with the changed material available for the next join. Moving instruction tiles into a queue and pressing Run would test process programming. That could be a different successful game, but it does not test the present physical-combining claim.

### C. Geometry-sensitive joining

**Small playable question:** which two pieces should touch, and how should their join be arranged so the resulting object does something useful? Begin with a few chunky pieces, forgiving snapping and one visible gap or load. Joining, bracing and reusing the joined object remain the verbs. Geometry must change the composition's behavior, not just its appearance.

**Prediction with all join rules revealed:** the same pieces call for a different joint/orientation when a support or load position changes. A player predicts a local weakness, then repairs it by combining another piece with the actual construction. Material identity alone cannot determine the result's usefulness.

**Tiny experiment:** two piece/joint behaviors, three visible support/load layouts, two reasonable constructions per layout. Compare an arrangement-sensitive model with a model that evaluates only the constituent multiset. Also compare forgiving snap placement with exact placement. Preserve the structure after a failed load so the next join can address its failure. Record which joint changes the outcome, the on-screen cue to its behavior and an alternate construction's cost.

**Strongest reason to discard:** either arrangement does not matter, or difficulty reduces to finding a narrow pointer coordinate. If forgiving placement eliminates the entire challenge, the experiment has found an execution task rather than the intended structural inference. Deliberate execution skill remains a possible future direction, but an awkward hit target is not evidence for it. If realistic physics needs many hidden thresholds, use a simpler truthful structural rule or abandon the candidate.

**Tangible-performance check:** snapping two actual endpoints must form a manipulable joint and result. Choosing “triangular brace” from an output card while the program assembles it repeats the rejected delegation problem. Rotating or positioning an actual joined construction can belong to combining when that geometry causes its behavior.

## Grader additions worth implementing before calling a winner

These are proposed checks, not completed results. Add them to the evidence-card format in [evaluation.md](evaluation.md); do not combine them into an enjoyment score.

| Check | Evidence to retain | Counterexample the grader must recognize |
| --- | --- | --- |
| Recipe exposure | Exact public pair/result/condition information shown before each commitment; preview versus actual result. | A candidate looks deep only when legality or state is concealed. |
| Context sensitivity | Two saved matched states, the changed public fact, preferred branch in each and actual continuation effects. | Only targets are renamed or reward weights are swapped; the same causal plan remains dominant. |
| Distinct composition | Outcome-relevant resources, topology, process state and capabilities; normalize independent action order. | Forty sequences are interleavings of one mandatory chain. |
| Plausible recovery | A public reason the mistaken action was reasonable, a replayed continuation and its cost. | Undo alone is counted as strategic recovery, or an innocent opening secretly makes success impossible. Undo remains useful handling. |
| Useful acquired relation | A later choice changes because the earlier relation is used in a new context; an optional short prediction made before feedback. | A fresh name or collection entry is called learning. A displayed exact outcome alone is called understanding. |
| Chore candidate | Consecutive solved prerequisites/unchanged waits, their state context and whether the player could skip them. | Repetition in meaningfully different contexts is automatically condemned; raw activity is rewarded. |
| Performed combination | Picked objects, inspected contact, released pair/joint, result position and subsequent handling in the browser trace. | An output command or model API transition earns gesture credit. |
| Human correction | Owner's praise for inspectable partners/results stays explicit beside conflicting AI reports. | The grader suppresses enabling information because an agent calls it too directive. |

A source-informed screen should name one worthwhile decision and its strongest trivial explanation. A browser player must then face the ordinary visible interface without a privileged rules packet. Mechanical screening can reject a forced script or false affordance cheaply; it cannot validate the desired visceral feeling. The owner's positive response establishes a discoverability preference, while enjoyment of the next challenge remains unknown until someone actually encounters it.

## Decision after this research pass

Keep full inspectability, unlimited material access and the physical gesture fixed. The earlier recommendation to try allocation is withdrawn after the user's explicit rejection of stock management. Screen geometry for meaningful composition with repeated raw templates; distinguish a compound that cannot extend into the target from the session, which can always continue with another copy. If unrestricted combining leaves only scripts or pointer chores, discard geometry rather than add a scarcity workaround. A negative result earns a design change, not a more flattering grader.
