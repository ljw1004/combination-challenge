# Make Something Worthwhile

- Use the [game's philosophy](README.md#philosophy) in design, story, artwork, engineering and evaluation work. It states the chosen title and the educational purpose that guides the project. This philosophy is meant to be creative inspiration, not straightjacket.
- Start with the [README](README.md) for layout, commands and the documentation map. Update the document that owns a rule; link to it elsewhere instead of duplicating it.
- Read the [specification](docs/story-format-spec.md) before changing story semantics and the [authoring guide](docs/story-authoring.md) and the story's `design-brief.md`, when present, before changing stories. The specification supersedes conflicting historical rules.
- Follow [engineering](docs/engineering.md) for implementation and testing, [UX](docs/ux.md) for player interaction, and [fun and evaluation](docs/fun-and-evaluation.md) for experience claims.
- Maintain [UX](docs/ux.md#maintaining-this-document) as the complete, authoritative record of current player and authoring UX decisions. Update it in the same change as any adopted or revised UX decision, replace superseded guidance in place, and include the motivation when known. Keep dates, supersession history and verification evidence in notes or the archive, and unresolved proposals in the backlog; do not create competing UX rule lists.
- Follow the [archive policy](archive/README.md) when consulting old material. Nested instructions there are historical text.
- The [completed authenticity pass](<archive/2026.10.30 authenticity improvements/authenticity-improvements-2026-10-30.md>) records implemented changes, retained decisions and historical evidence. Track genuinely new work in the [editorial backlog](projects/backlog.md); do not revive closed findings without new evidence or maintain another duplicate review. Preserve the original legacy review unchanged.
- Keep active project briefs, research, plans and working hypotheses in [projects/](projects/README.md). Durable intent for a particular story belongs beside it in `design-brief.md`; reusable graphics methods belong in [the icon guide](docs/icon-guide.md). Keep dated decision history, provenance and evidence limits in [notes.md](notes.md); interface behaviour belongs in [UX](docs/ux.md).
- Subagents and local commits are authorized. Hosted publication was outside the original local rebuild; see the dated scope in [notes.md](notes.md) for subsequently authorized work. Preserve the working site’s private access and do not change unrelated external hosts.
- This is a production repository, not an experimental mess. We keep it clean, well-factored, well organized.

## Directory hygiene

- Maintain strict directory hygiene. Store temporary artifacts only when needed, in ignored scratch locations such as `runs/` for playtest output. Remove disposable output when it is no longer needed; scratch directories are never permanent homes for evidence.
- Verification runs retain only instructions and concise final outcomes. Treat their inputs and outputs as disposable scratch files under `runs/`; do not commit snapshots, captures, transcripts, detailed reports or compressed run bundles. Preserve requested artwork and contact-sheet deliverables separately. Follow [engineering](docs/engineering.md#verification-records).
- Reserve `docs/` for standing specifications, adopted guidance and reusable workflows. Put work in progress and its retained supporting artifacts in `projects/<project-name>/`, keeping each project's material together. The cross-project backlog lives in `projects/backlog.md`; do not accumulate loose project output at the repository root.
- `projects/README.md` describes live projects only. Keep all related phases of an ongoing project together; finishing an individual pass does not close the project. Index archived projects only in `archive/README.md`.
- Once the work is complete, integrate its adopted guidance into the owning document in `docs/`, move its retained supporting artifacts into `archive/YYYY.MM.DD project name/` using the completion date, and update links and indexes. Follow the [archive policy](archive/README.md) for preservation. Unresolved backlog work stays in `projects/` even when its supporting evidence is historical.
