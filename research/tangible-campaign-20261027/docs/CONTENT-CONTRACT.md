# Content contract v1

Use JSON matching ../schema/scenario.ts. All IDs are unique stable lowercase strings. Item IDs and location IDs must be distinct. Locations are referenced as `@location-id` only when they are an operand in recipe a/b. Ordinary two-item recipes are commutative. `at` requires the acted-on target to be placed at that location (A+B at P); a recipe without `at` does not silently change by location. Ambiguous pair/setting rules are rejected.

Create recipes have `out`; installation recipes instead have `install:{target:ITEM_KIND,slot:SLOT_ID,component:ITEM_KIND}`. The two operand kinds must match that target/component. A slot is declared on the target Item. Required slots gate its declared capabilities until all are filled. Installed parts grant only slot-declared capabilities, not every capability of arbitrary nested parts. Required slots are unnamed in player view until filled; optional empty slots are hidden. An installation is counted as one successful combination, separately from creating a new item. Components remain outside if still useful; otherwise they are incorporated. To upgrade a slot, explicitly list compatible successive components in its accepts list; each different installation is a distinct recipe.

`retire` is only for a conceptual upgrade/incorporation, with a reason. The engine never auto-hides terminal things. It removes an explicit retired input only when no unfinished recipe or remaining objective still needs that exact kind/capability. Items and discoveries are globally unique, including incorporated components; recipes never recreate an already discovered output. Historical retained item states are not reset between stages.

Each stage introduces an adjacent physical area and explicit current objectives. `create` accepts a held item or genuinely capable enhancement; `place` needs that item/capability actually at the stated location. Each objective is conjunctive with the others. There is no choose-N field. Gold follows currently satisfied objectives only, not historical completion or precursors. A stage may have multiple alternative recipes producing useful outcomes without an arbitrary choose-two quota.

Initial supplies are initialItems. Later primitive supplies need a named cache with contextual narrative and broad plausible contents. A cache ID opens once. Locations appear only where declared in a stage, remain fixed in that area, and are never duplicated or teleported. Previously visited areas can be revisited with selected actual carried things. Stage advance carries useful existing things as one translated group; default is conservative future usefulness. Optional stage `carry` lists kinds of existing things to take instead, never creates them; authored carry must preserve a legal future route. This lets trials diagnose over-carrying rather than hide things. Empty old areas persist in world state.

Source/caveat metadata is developer evidence, not chronology asserted by the engine. Recipe descriptions appear only after discovery. Player interface exposes current things, motivation, explicit objectives, available areas and compatible partners, never unknown output names or hidden recipe IDs. Debug checkpoints are legal action replays, not injected state.

### Readiness and physical continuity
A recipe may require `{item,capability}` on one of its own two operands. This is an actual property of a construction, not an invisible third ingredient or stage gate. Required construction slots gate its capabilities; slot `grants` maps a fitted component ID to the capabilities that particular component confers. Slots remain blank in the player view until filled.

Automatic chapter carry takes only objects actually present in the departure area. It never retrieves an object left in an earlier area; use explicit travel carrying the selected real tools. Earlier locations never move. Conservative default carry may carry more objects than the intended route requires; that is a clutter diagnostic, not a reason to hide objects. Explicit carry lists cannot override physical continuity.

Separate move/placement counts, unique successful recipe counts, unique creations, and installation counts are retained in append-only event evidence. Undo does not erase effort or count the same recipe twice. Restored state validation is structural, not proof that arbitrary external save edits were honestly played.
